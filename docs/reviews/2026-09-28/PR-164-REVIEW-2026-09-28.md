## 1.（P2）闸拒绝**完全无声**，而「留给下次启动认领」在本进程内不成立

`#dispatch()` 拒绝时是裸 `return`：无日志、无 trace 事件、无返回值。而 `draining` 是**单向闩**
（`DrainGate` 只有置位，没有复位）。于是有一条宿主侧没被写下来的义务。

**探针**（`drain()` 返回 false ——即**排空没完成**——宿主却没退出）：

```
① drain() = false
② approve 后记录状态 = running / ownerId 是本进程 = true
③ resumePending 认领数 = 0        （ownerId === 本进程 ⇒ resume-policy 判 own-process 跳过）
④ submit 再提交 = runner 正在优雅停机，不再接受新任务
⑤ 记录终局 = running              （本进程内无任何自愈路径）
   awaitTask（300ms 超时收口）= 仍未终态 —— 永久挂起
```

即：**这条记录停在 `running`，本进程再也跑不起来、也再也认领不回来**，只能等下一次进程启动。
外部观测面还会说错话：记录里的 `ownerId` 是本进程，但它的流从未被 `#streams.open` 打开过 ⇒
客户端订阅它拿到的是 `stream.unavailable{reason:'not-in-this-process'}`（「别的进程在跑，你去轮询」），
然后对着 `GET /tasks/:id` 永远读到一个 `running`。

**为什么会咬人**：修前 `approve` 在窗口里是照跑的（先跑起来、再被退出的宿主硬切）；修后改成
「留给下次启动」，这个改动**把正确性押在「宿主收到 false 一定退出」上**。而：

- `examples/*/src/main.ts` 确实是 `process.exit(0)`（无论 clean）—— 参考宿主是对的；
- 但**没有任何文档写下这条义务**。`docs/transport/drain-gate.ts` 里那句
  「超时返回 false 但**不改任何共享状态**」甚至会让人读出相反的意思（`draining` 恰恰被永久置位了）；
- `docs/usage-guide.md` §7 那句「停机后 `POST /tasks` 回 503 …… 任务没丢」在宿主不退出时不成立。

**建议**（两条都便宜）：

1. 拒绝那一刻**出声**。这个仓库的核心价值是「不静默」—— 但这里连一条 `console.warn` 都没有，
   运维只看到一个卡在 `running` 的任务。哪怕只在 `#dispatch` 里记一次「已停机、把 task X 留给
   下次启动认领」，也从「无从解释」变成「一眼可解释」。
2. 把义务写进契约（`drain()` 的 JSDoc + `usage-guide` §7/§6.5）：**`drain()` 是单向闩；返回
   `false` 意味着本进程此后不能再推进任何任务，宿主必须退出**（否则滞留记录不会自愈）。
   顺带订正 `drain-gate.ts` ② 那句「不改任何共享状态」。

> 不是「必须把 false 也当成能继续服务」—— 那是错的语义。要的是**让宿主无法误读**。

## 2.（P2）守卫有个盲区：`#executeInner`

守卫钉住了 `this.#execute(`（全文件恰好 1 处，落在 `#dispatch` 内），但**没钉 `this.#executeInner(`**。
后者是同一个旁路的另一半，而且后果更重：

```ts
async #execute(rec) {            // ← 只有这里做「同步认领 + #streams.open + active++」
  …
  this.active++;
  await this.#executeInner(rec); // ← 目前恰好 1 处（已核实）
}
```

下一次新增恢复路径时，如果有人写 `void this.#executeInner(rec)`，它会**同时**绕过：

- 停机闸（就是本 PR 修的那类 bug，原样复活）；
- `active++` 与 `#streams.open` ⇒ `drain()` 会在一条 run 真在跑的时候返回 `true`，
  且 `GET /tasks/:id/stream` 对着一条正在跑的任务说 `not-in-this-process`。

**建议**：守卫的判据从 `this.#execute(` 扩到 `/this\.#execute(Inner)?\(/`，断言 2 处、且各自落在
自己的家里。改动 3 行，覆盖的是同一类失效模式的完整面。

## 3.（P3·文案）`submit` 那条「窄窗口」是一个不存在的窗口

提交信息、CHANGELOG、`async.ts` 注释三处都写了：`submit` 走 `#dispatch` 是为了挡
「**进闸与派发之间刚开始停机**的窄窗口」。但 `submit` 是**完全同步**的函数：

```ts
submit(input, opts): TaskRecord {          // 没有 async、没有 await
  if (this.#drain.isDraining) throw …;     // 顶部：拒绝语义（对的）
  …
  const saved = this.store.save(rec);      // 异步 store 也只是挂个 .catch，**不 await**
  this.#dispatch(rec);
}
```

同步段内 JS 不可能插入 `drain()` 的置位 ⇒ 那个窗口在 `submit` 里**不存在**，这道闸在那里
永远不触发。走 `#dispatch` 仍然是对的（统一结构、少一条例外），但理由是假的 ——
按本仓「注释改成真话」的标准，应当直说：**`submit` 是同步的，这里的闸是结构一致性，不是行为依赖**。

## 4.（P1·未提交层）P3-1 的增量 marker **打破了折叠不变量**

`tests/engine/trace-events.test.ts` 开篇钉的正是这条：

> 把一次 run 的全部 `TraceRecordEvent` 按 `seq` 升序折回一条 trace，必须**逐字等于**收尾时
> `snapshot()` 的那条……任一处记账点被改成「绕开派发」，这里就红。

新 marker 以 `span.event` 帧派出，却**没有**写进 `span.events`。探针（`maxEvents: 3`，10 条事件）：

```
① marker 帧    : {"type":"span.event", …, "event":{"name":"trace.truncated","body":{"limit":3}},"seq":5}
② 折叠后 run 根: [x,x,x, {trace.truncated, {limit:3}}]                 ← 增量视图
③ snapshot 根 : [x,x,x, {trace.truncated, {droppedEvents:7,limit:3}}]  ← 终态视图
④ fold === snapshot ? false
```

两个问题叠在一起：

1. **增量与终态不同源**了（同一个名字、两种 body）；marker 落在「丢弃发生的那条 span」上，
   而摘要恒在 run 根 —— 若丢弃发生在子 span，两条 `trace.truncated` 连 span 都不同。
2. **同一个事件名承载两种形状**，消费方无法靠 `name` 区分「位置信号」与「最终计数」。

而新用例只断言「marker 出现了」，**从不折叠** ⇒ CI 全绿。这恰好是上一轮报告点的那种失效模式：
完备性靠「我检查了我想得起来的那一面」。

**建议**：让 marker 成为一个**独立的控制帧**（如 `{ type: 'trace.truncated', limit, seq }`，
不进 `span.event` 命名空间），`fold()` 显式跳过控制帧，并补一条
「`traceLimits.maxEvents` 超限时，**记录事件的子序列**仍折得逐字等于 snapshot」的用例。
这样「增量与终态同源」从散文变成断言，marker 也从「骗折叠器的事件」变成「标明缺口的信号」。

## 6. 做对了、值得保留的取舍

- **`approve` 整批拒 + 一字不动**：用例断言的是记录 JSON **逐字节不变**（连那个合法的 id 也不收） ——
  比「挑着收」安全，且与 `parseApproveBody` / `parseEventBody` 同纪律；
- **拒绝加常量上限**：理由成立（单次输入无法放大体积），而且第二轮**自己订正**了第一版论证里
  「`|approvals| ≤ |pendingApprovals|`」这个跨轮不成立的断言 —— 这种自我订正比修 bug 更值钱；
- **校验顺序对**：409（状态不对）排在 400（入参不对）之前 ⇒ 「已处理过的 approve 重放」
  仍拿到 409（正确语义），不会退化成误导性的 400。这一步没写进注释，但它是对的；
- **守卫带真空护栏**（源码长度 + `AsyncRunner` 本体在场 + 调用次数下限）——
  「正则一旦失效就永远绿」是这个仓自己点名过的最糟形态，它躲过去了；
- **`timer` 分支文案订正**：原文案「（或先 approve）」指了一条对 timer 挂起根本走不通的路
  （原因闸会 409）。改成「到点自己醒来」是真话。
