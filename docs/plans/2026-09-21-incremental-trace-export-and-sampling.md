# 增量 trace 出口 + 采样/记录成本 —— 设计

> **状态**：设计待拍板（分叉见 §6，§6.1 与 §6.2 是最想听意见的两条）。
> **上游**：`docs/spec.md` §9.3（产出与导出）、§9.4（开放问题「全量记录成本 vs 截断/采样默认阈值」）、
> §9.2（上下文传播）；`docs/plans/2026-09-11-agent-service-hardening.md` §7 F3 的两条后置项；
> `docs/observability.md` §0/§4（「采样不内建，是配方 2.3」这条既有决策）。
> **本文覆盖两件事**，它们同属「可观测支柱的出口方向」，但**改动面不相交**，落地时是两个独立 PR：
> **A. 增量 trace 出口**（并把 `GET /tasks/:id/stream` 从"后置"变成"落地"）
> **B. 记录成本与采样**（把 §9.4 从开放问题变成决定 —— 注意 **B 不新增采样器**，理由见 §2.2 末与 §3 Phase B2）

---

## 1. 目标

- **A**：让「等不了 run 收尾」的消费者拿到**增量**记账事件 —— 终端面板、SSE 前端、异步任务的进度流。
  兑现性质：`POST /run`（SSE）能下发**全量事件粒度**（F3 当初判「架构代价大、后置」的 B 方案），
  并新增 `GET /tasks/:id/stream`。
- **B**：回答 §9.4 —— 给出**默认阈值**的决定、让「少记了数据」这件事**可数**（不是静默）、
  并把「采样率该定多少」从拍脑袋变成**可算**（用 trace 体积的实测数字换容量）。

两件都不改既有行为：A 是新增出口（既有帧名逐字不变），B 是新增一个选项 + 文档/示例收口。

## 2. 现状证据（都是实读/实测，不是印象）

### 2.1 A：增量出口为 0

```
grep -rn "onSpan|onEvent|onTrace|subscribe" src/ --include=*.ts   → 0 命中（只有无关的注释/其它词）
grep -n "stream" src/transport/http-route.ts                     → 0 命中（无 /tasks/:id/stream 路由）
```

- `TraceRecorder`（`src/engine/tracer.ts`，192 行）的记账面是**私有数组 + Map**，
  唯一出口是 `snapshot(status): Trace` —— 也就是说**记账与交付之间没有任何缝**，
  run 收尾时由 `runtime/run.ts::flushSinks` 把整棵 trace 交给每个 sink（sink 抛错被吞，第 312 行）。
- 同步 `/run` 的 SSE 帧只有三个：`text.delta` / `run.end` / `error`（`src/transport/http.ts`）。
  逐字对应 F3 决策 **A**（「只 `text.delta` + `run.end`」），B 方案（全量事件粒度）被记为
  「**需要把 trace 事件实时外推，架构代价大，后置**」。
- 异步任务流式（`GET /tasks/:id/stream`）在 F3 里**同一条**理由下后置
  （计划原文：「需要 run 进度跨进程，属『run 内事件流』，不在本期」）。
- `TaskSink`（`transport/async.ts:45`）只提供 `onFinished(rec)` —— **收尾**回调，不是进度流。

**所以 A 的真实缺口不是"加个 SSE 端点"**，而是**记账面没有订阅缝**：没有它，端点无论怎么写
都只能靠轮询 store 猜进度。

### 2.2 B：成本是「线性但可放大 13.7 倍」，计数无上限；而采样**已经有主**

实测口径：`scriptedClient`（零 token、零网络）+ 每次工具调用返回约 1 KB / 37 KB 结构化数据，
量的是 `JSON.stringify(trace)` 的 UTF-8 字节（`npm run bench:trace`，见 §「验证与复现」）。

**小出参（约 1 KB/次）**

| 口径 | 工具调用 | span 数 | 事件数 | trace 字节 | 字节/事件 |
|---|---|---|---|---|---|
| 缺省 | 0 | 2 | 0 | 1 176 | — |
| 缺省 | 1 | 3 | 2 | 3 655 | 1 828 |
| 缺省 | 5 | 7 | 10 | 13 568 | 1 357 |
| 缺省 | 20 | 22 | 40 | 50 760 | 1 269 |
| 不截断 | 20 | 22 | 40 | 50 789 | 1 270 |
| 截断 200 | 20 | 22 | 40 | 20 887 | 522 |

**大出参（约 37 KB/次），5 次工具调用**

| 口径 | trace 字节 | 最大单事件 | 相对缺省 |
|---|---|---|---|
| 缺省（截断 2000 字符） | 17 113 | 2 540 | 1.0× |
| **不截断（`maxEventChars: false`）** | **233 797** | 45 871 | **13.66×** |
| 截断 200 字符 | 6 125 | 337 | 0.36× |

三条可用结论（这是 B 的全部依据）：

1. **成本 ≈ 事件正文**。0 次工具调用的底噪是 1.2 KB（run + 1 个 turn 的 span 骨架）；
   之后**每次工具调用 +1.3~1.8 KB**（小出参）——**90%+ 的字节是 `tool.input` / `tool.output` 的正文**。
   span 数本身（每回合 +1，每工具调用 +0）不是成本来源。
2. **真正会失控的是宿主显式打开的两件事**：`maxEventChars: false`（13.66×）与**长跑**
   （线性外推：100 次工具调用 ≈ 250 KB 小出参、≈ 4.7 MB 大出参）。缺省截断下，
   线性增长本身是可接受的。
3. **计数侧一行代码都没有**。`maxEventChars` 管的是**单个事件正文长度**；
   **事件数量**（= 2 × 工具调用，随 run 无限增长）在框架侧**没有任何上限或计数** ——
   也就是说 `maxEventChars: false` + 长跑这条组合可以无界放大，而宿主侧看不到任何迹象。

**而「采样」这一半已经有主，本轮不能再造一个：**

- `docs/observability.md` §0 的表格里**采样那一行明写 ❌ → 配方 2.3**（「框架不内建」），
  §4 边界再写一次「框架不内建日志层 / 采样 / 脱敏 / …… 那是宿主职责」。
- 配方 2.3 **已有成品实现**：`examples/observability/src/index.ts` 的 `sampleSink`
  —— 按 `traceId` 确定性哈希、`rate` 校验、**失败 run 永不采样掉**、`fanOut` 给下游。
  并且 `tests/docs/observability.test.ts` 用**反向全覆盖**把这四个工厂钉在文档里。
- 所以「框架缺一个采样器」**是个假缺口**。真缺口只有两条：**采样率没有依据可算**，
  和**被丢掉的那部分没有任何计数**（宿主不知道"少了一半"）。

另外一条与 B 直接相关的既有事实：

- 出站 `formatTraceparent` 的 flags **恒 `00`**，`core/trace.ts` 给的理由是
  「本框架**不采样**（每次 run 全量记账），故没有『已采样』可声明」。
  **这条理由的措辞在采样成为明确推荐配法之后不再严谨**，是个必须写死的口径（见 §6.2）。

## 3. 分阶段（顺序即理由）

### Phase A1 —— 记账面开一条订阅缝（唯一的机制改动）

`TraceRecorder` 增加订阅，派发**记账事件**（不新增数据结构，事件体直接引用既有形状）：

```ts
export type TraceRecordEvent =
  | { type: 'span.begin'; seq: number; span: Span }                    // 此刻 endedAt 未定
  | { type: 'span.end';   seq: number; span: Span }                    // 收尾后形状（status/error/usage 已在）
  | { type: 'span.event'; seq: number; spanId: SpanId; event: SpanEvent }
  | { type: 'span.attribute'; seq: number; spanId: SpanId; key: string; value: string | number | boolean };
```

四条硬约束（每条都有对应用例，见 §5）：

- **同步派发**：与记账同一 tick 调派发，**不 await**（订阅者是观察者，不该把 run 变成它的调度）。
- **吞掉订阅者抛错**：与 `flushSinks` 同款纪律（观测失败不击穿业务）。抛错的订阅者不影响其它订阅者。
- **无订阅者零分配**：`if (listeners.length === 0) return` 是**第一条语句** —— 「不订阅不付钱」要能测。
- **`seq` 单调递增**（recorder 内计数器，run 内从 1 开始，跨 span 全局单调）：
  它是「续订 / 重放 / 去重 / 与终态 trace 对齐」四件事的公共基础。**没有 seq 就没有 A 的可测契约。**

### Phase A2 —— 公共出口（两个选项，一个语义）

- `RunInvocationOptions.onTraceEvent?: (e: TraceRecordEvent) => void`
- `AppOptions.onTraceEvent?` —— 应用级缺省（构造期快照，与 `sinks` 同款语义）

**为什么不复用 `TraceSink`：** sink 的契约是「run 收尾拿到**完整** trace」，增量是**另一条缝** ——
它的消费者恰恰是「等不了收尾的人」。合并会让 sink 契约变成「可能收到半棵树的多次调用」，
既有 sink（OTLP / metrics / 落库）全部要重新理解自己收到的是什么。**新增一条缝 = 零迁移。**

⚠️ 文档要写死一句：`onTraceEvent` **不保证送达**（宿主自己的流断了就断了，
它没有 sink 的重试/兜底语义），也**不是** sink 的替代。

### Phase A3 —— 传输层（两条）

**同步 `POST /run` + SSE**：新增帧 `trace.event`（body 即 `TraceRecordEvent`），
既有三帧**逐字不变**（向后兼容：不订阅新帧的客户端行为零变化）。
**帧名取单数一族（`trace.event` + body.type），不取每类型一帧** ——
将来加新事件类型时，老客户端只是漏掉一种 type，而不是漏掉一种**帧名**（后者更隐蔽）。

**异步 `GET /tasks/:id/stream`（新增路由）**：

- 帧：`trace.event`（实时/重放）+ `stream.truncated`（缓冲超限明示）+ `task.end`（终态收口）。
- **从头重放**：订阅时按 `Last-Event-ID`（SSE 标准头，值为 `seq`）或 `?from=<seq>` 定位；
  缺省从缓冲里最旧的 seq 开始，然后转实时 —— 于是「连上就跑了一半」的客户端也能拿到完整前缀。
- **终态收口**：任务已终态 ⇒ 把缓冲发完 + `task.end` + 关闭。**不允许**留下一条永远不会再产出事件的流。
- **缓冲有上限**（`AsyncRunnerOptions.streamBufferEvents`），超限**丢最旧**并发一条
  `stream.truncated { droppedBefore: seq }` —— 明示，不静默。
- **背压不 abort 任务**：复用 `sseWriter` 的 `maxBufferedBytes`，但收口时**只关这条流**。
  这是与 `/run` 的 SSE 的**关键差别**（那里流的下游就是 run 的所有者，背压等于「别烧 token 了」；
  这里流的读者是个旁观者，任务不该因为看的人慢而变慢）。
- **跨进程边界（明确写进文档，不假装）**：事件缓冲在**跑任务的进程**内存里。
  另一进程服务这条流时，只能回「任务当前状态 +（若已终态）立即 `task.end`」+ 一条
  `stream.unavailable`，**不假装实时**。为什么不做事件落库：实测事件数 = 2 × 工具调用、
  正文 KB 级 ⇒ 每条工具调用要把 KB 级正文写库两次（写放大），而宿主手里本来就有
  Redis Streams / Kafka（Phase A2 的 `onTraceEvent` 就是给它们的缝）。
  这与本仓「给缝不给子系统」同一条线。

### Phase B1 —— 让「少记了」可数（先能看见，再谈少记）

新增 `traceLimits`（`createApp` 级 + run 级覆盖），**只管数量**：

```ts
export interface TraceLimits {
  /** 整条 trace 的事件总数上限（`tool.input` / `tool.output` / `score` / … 都算） */
  maxEvents?: number;
}
```

- 超限行为：**停止记账**（后续事件不再进 trace）+ 在 run 根上记一条
  `trace.truncated { droppedEvents, limit }` —— 这条**最后写入**（超限后仍进得去），
  于是「看板上少了一半数据」终于有人能收到（与 OTLP `partialSuccess` 那条修复同因）。
- **不做环形缓冲（丢最旧、留最近）**：那会让 trace 中间出现空洞，而空洞比「尾巴截断」
  难解释得多（「这一回合怎么没有工具事件」vs「末尾被截断了」）。**缺口位置可预测 + 有计数**才叫可解释。
- `Trace.totalUsage` 不受影响：token 记账是 span 级字段，不靠事件。
- **与 `maxEventChars` 的分工要写清**（避免造出「0 的双重语义」那种债）：
  **长度**看 `maxEventChars`（既有，run 级），**数量**看 `traceLimits.maxEvents`（本版）。
  一个旋钮一个家，两个都是「不设 = 不限」。

### Phase B2 —— 采样：**不内建**（既有决策），补「可算」与「可数」

**不做**框架级 `samplingSink`。理由三条，任一条成立就够了：
① `spec §9.3` 与 `docs/observability.md` §0/§4 已明确「采样是宿主职责、是配方」；
② `examples/observability` 已有成品 `sampleSink`（确定性哈希 + 失败必留 + fanOut），
再造一个就是**同一件事的两份实现**（本仓最忌讳的那种债）；
③ 框架内建采样会与「记账全量」的卖点正面冲突（框架**恰好**只该管记账侧的截断）。

本轮 B2 实际做三件小事：

1. **可算**：`docs/observability.md` 配方 2.3 增加一张**换算表** ——
   用 §2.2 的实测数字给出「每条 trace 多少 KB → 每天多少 GB → 对应采样率」，
   并写明**采样率要按容量预算倒推**，不是拍一个 0.1。合成一句可执行的判据。
2. **可数**：`examples/observability` 的 `sampleSink` 增加**丢弃计数**（`dropped` 计数 +
   可选 `onDrop` 回调），与 B1 同因 —— 「被采样掉的那部分」必须能报出来，
   否则它和「本来就没跑」在监控上无法区分。同步更新 `docs/observability.md` 配方 2.3 的文字。
3. **一句建议进配方**：想让看板能自证「这条为什么在」，让采样闸门把决策写进**一份拷贝**
   （与 `redactSink` 的深拷贝同款；不修改原 trace，否则下游 sink 看到的东西和记账不一致）。

### Phase C —— 文档与记录收口

- `usage-guide`：`traceLimits` 进选项表 + §7 边界一条（数量上限与丢弃计数的语义）。

- `spec`：§9.4 **收口**（从「开放问题」改为「已决定」）、§9.3 补一句「增量出口 = `onTraceEvent`，
  与 sink 是两条缝」、§10 记决策（含 §6.2 的 flags 口径与 §5 的反向验证记录）。
- `AGENTS.md`：布局里补 `engine/` 的 tracer 订阅、`transport/` 的两个流式端点。
- `api.html`：新增导出（`TraceRecordEvent` 类型）进导出表（反向全覆盖守卫钉着）。

## 5. 测试策略

**A 的核心不变量（最重要的那条）**：把一条 run 的**全部增量事件**按 `seq` 折叠成一条 trace，
必须**逐字等于** `snapshot()` 的结果（同一个 recorder、停止记账之后比对）。
它一次钉住四件事：不丢、不重、顺序正确、增量与终态同源。
反向验证（必须真红）：**把任一记账点改成绕开派发**（例如 `setAttribute` 直接写不派发）⇒ 折叠结果与
snapshot 不等 ⇒ 用例红。

其余用例：
- `seq` 严格单调、无重复；`span.begin` 早于同 span 的 `span.end`；`span.event` 落在两者之间。
- 无订阅者时**零派发**（用一个计数 spy 断言：订阅前跑一段，事件构造次数 = 0）。
- 订阅者抛错 ⇒ run 照常成功、其它订阅者照常收到（两条订阅者，一条抛）。
- 并行工具（`maxToolConcurrency > 1`）下事件的父子关系不乱。
- `/tasks/:id/stream`：从头重放 / `Last-Event-ID` 续订 / 终态收口 / 缓冲超限发 `stream.truncated` /
  **背压收口但任务继续跑**（这条最容易写错，必须专门用例）/ 跨进程边界帧。

**B 的用例**：
- `traceLimits.maxEvents` 边界：缺省（不限）、恰好等于上限、0（= 一条都不记，但有计数）、负数/非整数 →
  响亮失败（沿用 `resolveMaxRetries` 那套「坏值不静默」的口径）。
- 计数对账：`trace.truncated.droppedEvents` == 实际被丢弃的事件数（用受控事件数造）。
- 反向验证：摘掉「超限记一笔」⇒ 红。
- 示例 `sampleSink` 的丢弃计数：`rate: 0`（且非错误）⇒ 计数 = 丢掉的条数、下游没收到；
  `rate: 1` ⇒ 计数 0、下游全收到；错误 run 在 `rate: 0` 下仍保留且**不计入丢弃**（否则「失败必留」
  这条文案与计数互相打脸）。

## 6. 分叉表

| # | 分叉 | 选项 A | 选项 B | 推荐 |
|---|---|---|---|---|
| 1 | 增量出口的形状 | `TraceRecorder` 订阅（记账点唯一，engine 零改动） | engine 里直接调宿主回调（散布 5+ 处记账点） | **A** |
| 2 | SSE 帧名 | 每类型一帧（`span.begin` / `span.end` / …） | 单帧 `trace.event` + body.type | **B**（将来加类型老客户端只是漏一种 type） |
| 3 | 跨进程实时 | 事件落 store（真跨进程实时） | 内存缓冲 + 明确边界 + `onTraceEvent` 给宿主自己转发 | **B**（KB 级正文 × 2/工具调用的写放大，且宿主本来就有总线） |
| 4 | 缓冲超限 | 丢最旧 + `stream.truncated` 明示 | 背压阻塞任务 / 直接断开连接 | **A**（任务不该被旁观者的速度拖慢） |
| 5 | 同步 `/run` 的 SSE 是否也带记账事件 | 带（超集，既有三帧逐字不变） | 不带（保持 F3 决策 A） | **A** |
| 6 | `traceLimits` 的落点 | 整条 trace 事件总数 | 单 span 事件数上限 | **A**（成本是整条 trace 的量） |
| 7 | 超限行为 | 停止记账 + 计数（尾巴截断，缺口位置可预测） | 环形缓冲丢最旧（中间空洞） | **A**（见 §6.1） |
| 8 | 采样器放哪 | 框架内建 `samplingSink` | **留在示例 + 文档**（既有决策） | **B**（§2.2 末：A 是与既有决策冲突 + 同一件事两份实现） |
| 9 | 采样决策是否落 trace | 框架替宿主落 | 只作为**配方建议**（宿主在拷贝上落） | **B**（框架对采样不该有观点） |

### 6.1 最想听你意见的分叉：7（超限时丢哪一头）

我选了「**停止记账 + 计数**」（尾巴截断）。理由是**可解释性**：某个上限触发后，
解释一句「超出部分未记录，计数 N」就能说清；环形缓冲造成的**中间空洞**要解释清得多
（「为什么第 7 回合没有工具事件而第 8 回合有」）。但另一头的代价要说清：
**长跑的尾部往往才是你要找的东西**（最后那次失败前的几回合），尾巴截断会正好砍掉它。

如果你更认同后者，改法很小：`traceLimits.mode: 'drop-new' | 'drop-oldest'`，两种都带计数。
**我倾向先只做 `drop-new`**（一个模式 + 计数已经让事情可解释），需要再加第二个模式 ——
而不是一上来给两个旋钮（这正是本仓在收的那种债）。

### 6.2 核心发现：`traceparent` 的 flags 必须继续恒 `00`，但理由要换

`core/trace.ts` 现在写的是「本框架**不采样**（每次 run 全量记账），故没有『已采样』可声明」。
在采样成为**明确推荐配法**（observability 配方 2.3）之后，这句话字面上不再成立 ——
**但它不能顺手改成「flags 跟随采样」**：

- 采样决策是**收尾后**的**导出**决策（配方里的闸门要看完好整棵 trace 才能判），
  而 `currentTraceparent()` 是**运行中**调的 —— run 期间**不可能**知道这次会不会被采样掉。
- 所以恒 `00` 是唯一不撒谎的选择，正确理由是：
  **「本框架不替下游声明采样状态：`sampled` 位描述的是『这条 trace 是否被记录』，
  而记录/导出决策发生在收尾之后、出站调用之前，运行期不可知。」**
- 顺带一条同样要写死的边界：采样采的是**导出**，不是**记账** ——
  被丢弃的那条 trace 在框架内仍然**完整记账**，只是宿主没把它发给下游 sink。

这条要进 `spec §10` 决策记录，否则下一轮很容易有人「顺手」把 flags 改成 `01`。
