## 0. 一句话

`agentia create` 出来的工程，**在开发期要能真的被调试**：**在现有 inspector 面板里**
选好输入（调哪个能力 + prompt + 目标目录）驱动一次 run，在 trace-view 里看清每一步的输入输出与工具调用，
且改文本资产不用重启。

典型场景（code-review）：**选文件夹 → 输入「帮我 review 一下代码」→ 看 trace**。
注意这类 agent 的 prompt 几乎不变，**变的是文件夹** —— 这个观察贯穿全文（§2.5、D3、D7）。

但 code-review 只是**一个**例子。一个工程里可以有多套子 agent / skill / prompt
（行程规划、code-review、查天气…），开发时要能调**单个**或**组合**，
而且**每个能力该不该多轮是它自己的事**（§2.5.1、D8）。

## 2. 先拆术语

### 2.1 三个「prompt」

「prompt 改了要重启吗」这句话有三种意思，答案完全不同：

| 名字 | 是什么 | 谁写 | 读取时机 |
|---|---|---|---|
| **输入 prompt** | 每次 run 的那句用户输入 | 开发者，运行时 | 每次 run |
| **资产 prompt** | `@Prompt` 拉取的 `.md` 文本 | 开发者，写代码时 | **每次模型拉取**（热） |
| **system prompt** | `@SubAgent` / 主 agent 的角色设定 | 开发者，写代码时 | 看写法：**值形态冻、函数形态热** |

### 2.2 四个层次（改动落哪）

| 层 | 是什么 | 本方案的改动 |
|---|---|---|
| **渲染层** `@migor/trace-view` | 纯渲染器，零依赖、`private`、官网 playground 与面板共用 | **无** |
| **宿主层** `inspector.ts` + `inspector-page.html` | CLI 所有；今天只收 trace | 对话流 + 输入条 + 写接口 + 读会话 + 鉴权 |
| **驱动层** `dev.ts` + 新增的 runner | CLI 所有；持有子进程生命周期 | 子进程重启 / IPC / **import 用户的 `app.ts` 并驱动它**（D9(d)） |
| **用户工程** `app.ts` / `main.ts` | 用户所有 | **只多一个 `app.ts` 工厂**（导出装配、接受选项）；**不含任何 dev 逻辑** |

> **渲染层不改**是硬约束：官网 playground 是**模拟**演示，它必须永远长不出「真跑 agent」的按钮。
>
> 第四层是这次新拆出来的：把「dev 逻辑放哪」从一个**框架/模板**问题变成
> **「CLI 驱动用户代码」**问题 —— 见 D9(d)。

### 2.3 两个「目录」（**这是最容易混的一个**）

| 名字 | 作用 | 今天的锚点 |
|---|---|---|
| **项目根** | `discover` 扫能力目录、`.env` 默认路径 | `process.cwd()` |
| **agent 工作目录** | 工具读写数据的那棵树 | **框架没有这个概念** —— 由工具代码自己决定 |

**关键事实**：`src/` 里按 cwd 解析的代码只有两处 —— `toolkit/env.ts:126`
（`resolve(options.path ?? '.env')`，相对路径按 cwd 解析）与 `toolkit/discover.ts:52`
（相对 discover 目录按 cwd 解析）。**框架不参与「工具看哪个目录」这件事。**
`ToolRunContext`（`core/tool.ts:126`）是封闭接口，没有任何 workdir 类字段。

⇒ 所以「切换文件夹」真正的问题是**「工具怎么知道该用哪个目录」**，不是「面板怎么把目录发过去」。

### 2.4 一条通则：热 vs 冻

贯穿本方案所有问题的一条规则：

> **在模块加载期读 = 冻（改了要重启）；在调用期读 = 热（改了立刻生效）。**

同一个坑在两处出现：`@SubAgent` 的 `system`（§3 F3）、工具的根目录（§3 F5）。

### 2.5 两种 agent 形态（**决定「历史」是什么意思**）

同一个面板要服务两种完全不同的调试方式，**混为一谈会把面板做错**：

| | **任务型** | **对话型** |
|---|---|---|
| 例子 | code-review（审某份代码）、批处理 | 助手、多轮追问 |
| 每次 run 的**变量** | **输入**（审哪份代码 / 哪个目录） | **上下文**（前面说过什么） |
| prompt | **几乎不变**（「帮我 review 一下代码」） | 每次都不同 |
| 要跨 run 累积上下文吗 | **不要** —— 会把上一个仓库的评审串进来 | 要 |
| 「历史」意味着 | **run 历史**（每次独立、可回看） | **对话历史**（session 累积） |

⇒ **对任务型 agent，会话历史不是「没做」，而是「不该做」**（上下文串味）。
它要的是** run 历史**（面板今天已有：最近 50 条的 run 列表）+ **prompt 回显**。

⇒ 推论（D7）：**run 列表必须留着** —— 对任务型它就是主历史面。
会话历史应当是**按需出现**（**多轮开关打开时**才显示），不是默认布局。

#### 2.5.1 但这不是「两种工程」，是「两种能力」（**别按工程分**）

一个 `agentia` 工程里可以同时有多个子 agent / skill / prompt，它们**各自的形态可以不同**。
用户举的例子正是这样：

| 能力 | 形态 | 多轮？ |
|---|---|---|
| `code-review` | 任务型（审某份代码） | **不要**（跨仓库串味） |
| `weather` | 任务型（查一次天气） | 不要 |
| `trip-planner` | 对话型（逐步细化行程） | **要** |

⇒ 所以「要不要多轮」是**每个能力各自的事**，不是工程的属性，也不是全局开关。

**这直接推翻了一个容易犯的设计错误**：把「多轮」做成面板上的一个全局开关。
正确形状是：**面板的选择器让你挑「这次调哪个能力」，多轮随之而定** ——
任务型能力跑完即止，对话型能力才累积 session。

> 已定形态（D8）：能力**多选**；多轮开关的初始值 = 所选能力声明的 **OR**
> （只要有一个是多轮就默认多轮），**且开关上要标出来源**（`多轮·trip-planner`）——
> 混选时默认值有歧义，标注来源是为了不让你面对一个「为什么这次带了上下文」的谜。
> 声明本身落在 `src/dev.config.ts`（**数据**，不是逻辑）。

⇒ 也顺带解释了 G5：**调试单位是能力**（见 D8）。
「调单个」不只是「少加载几个工具」，而是「按这个能力该有的形态去调」。

```
   │  CLI 进程 · agentia dev                 │
```

| # | 缺口 | 证据 |

### S1 的细节（**动手前必须先补**）

任意网页都能这样打进来：

```js
fetch('http://127.0.0.1:PORT/ingest', {
  method: 'POST',
  mode: 'no-cors',                            // 读不到响应，但请求确实发出去了
  headers: { 'Content-Type': 'text/plain' },  // 简单请求 ⇒ 不触发预检
  body: JSON.stringify({ traceId: 'fake', spans: [...] }),
});
```

`Host` 会是 `127.0.0.1:PORT` ⇒ 过闸。随机端口只是弱混淆。

- **今天**：开发者访问的任意网页能往面板塞伪造 trace（影响：误导）。
- **加上 `POST /run` 之后**：同一手法能让本地 agent 跑**任意 prompt**。而那个 agent 手握
  `.env` 里的 `ANTHROPIC_API_KEY` 与项目自己的 fs/shell 工具 ⇒ 升级为 RCE 级。

⇒ 这不是「顺手加固」，是 G1 的**前置条件**。

| **装配税**（重建一次 app） | 探针 `scripts/bench-app-assembly.ts`（**保留**的可重跑基准，与 `bench:trace` 同档、不进 CI）：**2.6 ms** / 20 个能力（120 个 10.6 ms，≈0.08 ms/能力） |

> 探针跑完已删除，工作区干净。值形态还会**追加** `REPORT_HINT`、函数形态**不追加** ——
> 写断言时注意这个差异（我第一版就因此误红一次）。
>

## 4. 决策

### D0 · 鉴权（前置，独立可做）

**建议**：`inspector.ts` 加两道 ——

1. **`Origin` 校验**：缺省（同源导航）或 `http://localhost:*` / `http://127.0.0.1:*` 才放行。
2. **per-session token**：`dev.ts` 启动时生成随机 token，嵌进面板 URL（`/?t=<token>`），
   所有**写接口**校验它（读接口可选）。

**理由**：零依赖（`node:crypto`）、改动局限在 CLI 内、且**不依赖本方案其余部分**。
建议**即便不做 G1 也先补**，因为 `/ingest` 现在就可伪造。

**代价**：面板 URL 变长；刷新页面要带 token（`dev.ts` 打印的 URL 里已含）。

> **评审补充（2026-09-22）**：token 校验建议覆盖**所有**接口而不只是写接口 —— 读接口
> （`/api/runs`、trace 内容）同样不该对本机任意网页开放，校验成本为零。token 走 URL query
> 会在浏览器历史 / 截图里留痕：本机 dev 工具可接受，但它**不进任何会被提交的文件**
> （不进模板、不进配置、不进文档示例）。

> **评审补充（2026-09-22 · 第二轮）· token 不必走 URL（可选，非缺陷）**
>
> 既然面板本来就是**同源页面**，有个同样零依赖、且不留痕的形状：`dev.ts` 在响应里下
> `Set-Cookie`（`SameSite=Strict` + `HttpOnly`）—— 面板后续请求自动带上，token 不进 URL、
> 不进历史、不进截图。或者仍不放 cookie，让面板首帧从内联的 `<meta name="dev-token">` 读。
>
> 另外一处值得写清的归因：**`Origin` 校验那半条已经挡住了 D0 上面那段 CSRF 示范**
> —— 跨源 `fetch` 浏览器必带 `Origin`，且非简单请求会先预检。
> ⇒ token 的真正作用不是补 `Origin` 的漏，而是挡「本机**其它已沦陷的进程**」
> （它们能直接 `curl`，没有 `Origin` 这个约束）。这个威胁模型下 cookie 够用；
> 只有当你把威胁模型扩到「同机的另一进程能读到浏览器 cookie」时才需要换成 header。
> 写清这一点是为了避免后来者以为「`Origin` 没挡住，是 token 救的」而做出错误的加固取舍。

### D2 · prompt 怎么进 agent（**核心决策**）

两个方向。先说结论：**建议方向 I，并把 session 一起做掉。**

#### 方向 I · 重启式

面板 → `POST /run {prompt, 文件夹, 能力, 多轮}` → `dev.ts` kill 子进程 → 带新指令重启 runner。

> runner 是 **CLI 自带**的（D9(d)），它 import 用户的 `src/app.ts` 并把四个控件喂给
> `createApp` / `app.run`。所以「重启」重启的是 runner，**用户的 `main.ts` 完全不参与 dev 环**。

| 项 | 评价 |
|---|---|
| 改动面 | `inspector.ts` 加一个写接口 + `dev.ts` 加子进程重启 + 面板加输入条 + **新增 runner** |
| 框架 / trace-view | **零改动** |
| 多轮对话 | **靠 session 持久化**（见下） |
| 延迟 | 实测 ~0.7s（hello-world）；真实项目更高，但模型调用本身是秒级，增量占比不大 |
| 风险 | `tsx watch` 自己还会 spawn 子进程 ⇒ kill 要**连整棵树**（照搬 v0.7.0「`close()` 保证子进程已终止」的纪律）；不能吃掉已文档化的 `npm run dev -- "问题"` 透传（`spec.md:2241`） |

> **评审补充（2026-09-22）· watch 的所有权**：今天「文件变 → 重跑」归 `tsx watch`，方案落地后
> 「面板 `/run` → 重启」归 `dev.ts` —— **两个触发源就有竞态**（保存文件的瞬间恰好点了运行 ⇒
> 双双 spawn、端口 / SSE 串台）。建议把 watch 也收编进 `dev.ts`（`node:fs` 的 `watch`，零依赖）：
> 「重启」只有一条路径、一个所有者。这顺带解掉 G3b（`.md` 不在 tsx 的 import 图里 ⇒ 不被
> watch）：dev.ts 自己的 watcher 把 `**/*.md` 加进去即可，D4③ 的 `tsx --include` 临时手段
> 因此**不需要引入**（它本来就只是过渡，且与「文本热更新」语义冲突）。

**多轮怎么保住** —— 这是方向 I 成立的关键。框架已有会话持久化，而且是**程序内 `app.run` 可直接用**的：

```ts
// src/toolkit/module.ts:158 —— app.run 的选项里就有
session?: { store: SessionStore; id: string };
```

`SessionStore`（`src/runtime/session.ts:15`）只是个两方法接口（`load` / `append`），
**目前只有 `InMemorySessionStore`**（`:31`）—— 进程内，重启即丢。
⇒ 模板里加一个**文件后端**（~20 行，读写一个 JSON）+ 固定 `sessionId`，
**重启后对话历史接得上**。这是模板侧改动，**不碰框架**。

#### 方向 II · 会话式

进程常驻，prompt 走通道喂进同一个进程。通道候选：

| 通道 | 跨重启 | 问题 |
|---|---|---|
| stdin | ✗ | `stdio` 要从 `inherit` 改 `pipe` + 转发；`tsx watch` 重启后 stdin 就断了 |
| 文件轮询 | ✓ | 简单可靠；模板里长出一个轮询循环（用户得能读懂、能删） |
| node IPC | ✓ | 要**绕开 `tsx watch`**（`dev.ts` 直接 spawn 应用 + 自己 watch），等于接管 tsx 的活 |

代价：模板变复杂；`tsx watch` 与 `dev.ts` 的子进程所有权冲突要解决。

#### 为什么先做方向 I

1. 它把用户的核心抱怨（「每次都要重启」）拆成两个**可分别解决**的问题：
   - **重启开销** → ~0.7s，可接受
   - **多轮丢失** → 用 `session` 解决，**是框架已有能力**，不是新机制
2. 方向 II 的真正价值不是省那 0.7s，而是「同一进程里连续对话」—— 而这**恰好是 session 已经提供的语义**。
   也就是说：先把问题归因归对，会发现大部分痛点用已有能力就解决了。
3. 方向 I 不动框架、不改模板的启动结构（只加一个 store 后端），**爆炸半径小**。
4. 若之后确实需要方向 II，`POST /run` 这个接口可以**原样复用**，只是实现从「重启」换成「喂通道」。
   ⇒ 方向 I 不是方向 II 的弯路，是它的第一步。

**待你确认的点**：如果你要的多轮是「跨重启续上历史」⇒ 方向 I 够用；
如果是「同一进程内不重启地连续追问、且连内存态也要留着」⇒ 才需要方向 II。

> **评审补充（2026-09-22）· 方向 I 的隐性成本，与一个更优的「I/II 合并」形态**：
>
> 1. **每次 run 都重启 ⇒ 每次 run 都重新 `createApp`**。0.7s 是 hello-world 的数；
>    真实项目的装配要跑 discover + **MCP 连接器握手**（spawn server + initialize）——
>    MCP 重的项目每次运行多付几秒，stdio server 进程反复 churn。这不是模型时间，
>    是**每次必付的装配税**。
>    ⚠️ **实测修正（2026-09-22，见 D8 探针表）**：上面「多付几秒」**不成立**，且错得离谱 ——
>    discover + 装配 = **2.6 ms**（20 个能力；按 ~0.08 ms/能力 线性，200 个能力也才 +16 ms 量级）；
>    MCP 冷握手 = **78 ms**（连接器复用后只剩 0.3 ms）；整进程重启 = **674 ms，
>    其中 ~494 ms 是 node+tsx 启动本身**（与项目规模基本无关）。
>    ⇒ **这条的收益要改口径**：合并形态真正省下的是 ① 每次 run 那 ~0.5 s **进程启动**；
>    ② 不反复 spawn/收编 MCP 子进程（churn 与旧进程泄漏）；③ 消掉 watch 竞态。
>    这三条仍然成立、仍然值得做 —— 只是**别再用「几秒装配税」当理由**，
>    真要再快该啃的是**启动**，不是装配。
> 2. 顺着「watch 收编进 `dev.ts`」（上文评审补充）再想一步：watch 一旦归 dev.ts，
>    方向 II 否掉 node IPC 的理由（「要绕开 tsx watch」）就**不成立了** —— dev.ts 直接
>    spawn runner（tsx 不带 watch）就有天然 IPC。于是存在**合并形态**：
>    **runner 常驻 + IPC 收 run 指令 + 代码变更才重启**。它同时消掉：装配税（MCP 连接
>    保住）、watch 竞态、重启延迟；方向 I 担心的「多轮丢失」仍由 session 解决。
>    ⇒ 建议把「I 先行、II 以后」改为「直接做合并形态」；`POST /run` 的接口形状两者相同，
>    对外无返工。
> 3. **在飞 run 的并发语义必须定**（原文档未提）：面板连点两次运行 = kill 在飞的？排队？
>    拒绝？restart 式下「再点一次」意味着 kill 在飞 run —— 没有增量出口时这次 run 的
>    trace **整个丢失**（trace 是收尾才 POST 的）。建议：默认**拒绝并提示**（最安全），
>    kill 做成显式按钮。已登记进 §6 待定。

### D3 · 工作目录怎么表达

#### 先定位：它是**每次 run 的输入**，不是全局设置

以 code-review 为例，实际流程是：

```
选文件夹（审哪份代码） → 输入「帮我 review 一下代码」 → 看 trace 里每步的输入输出 / 工具调用 / 效果
```

注意那句 prompt **几乎不变**，变的是文件夹。⇒ 对任务型 agent：

- **文件夹是每次操作的主控件**，prompt 只是「一句固定命令 + 回车」。
- 两者都是**这次 run 的输入** ⇒ 在 UI 上应当**并排**（D7），而不是把目录藏进设置。
- 所以它天然是 **per-run** 的，不是「app 级全局配置」。`ToolRunContext` 恰好是 per-run 的。

#### 四个方案（**已定 D**，2026-09-22）

**已定 D**（零框架改动），把 **C** 推迟到「真的需要 per-run 时」再做。

| 方案 | 工具侧要写什么 | 热切吗 | 代价 |
|---|---|---|---|
| **A** `process.chdir()` | 裸相对路径 | 能 | **进程全局**：不能并发两个 run 指不同目录；主 agent 与子 agent 不能各用各的根；任何按 cwd 解析的东西跟着走（如 `loadEnvFile()` 的默认路径） |
| **B** 环境变量 | 每次调用读 `process.env` | 能 | 隐式、无类型；**不进 run 配置快照** ⇒ 面板看不到 |
| **C** `ToolRunContext.workdir` | 读 `ctx.workdir` | 能 | **框架公共面变更**（见下） |
| **D** **DI 注入** | 构造器收一个值，方法里用 `this.root` | 能 | **per-app 而非 per-run**；不进 `config.*` 快照（但 CLI 侧可记账） |

**A 应排除**：它把**项目根**与 **agent 工作目录**绑成一件事（§2.3），而今天两者都是 `process.cwd()` ——
这正是病根。需求是「项目还在原地，但让工具去看另一个文件夹」，chdir 是把整个进程搬走。

> **仓库自己就警告过这件事**。`src/toolkit/env.ts:17-19` 解释「为什么不塞进 `createApp` 自动读 `.env`」：
> 「读 `.env` 会改 `process.env`，而 `.env` 是按 cwd 找的。隐式生效后，
> **『同一份代码换个目录跑结果不同』**和『本地多放了个 `.env`，测试行为悄悄变了』
> 都会变成要花时间排查的悬案。」
>
> `process.chdir()` 把同一类悬案一次性放大到**所有**按 cwd 解析的东西上 —— 而且是在运行期悄悄发生的。

#### D（DI）为什么成立：**容器本来就支持**，一行框架代码都不用改

`ClassProvider` 有显式的 `deps` 字段（`container.ts:16-21`：「构造器参数对应的依赖 token（按序注入）」），
实例化时按 `deps` 解析（`:119-120`）。而能力实例**确实走容器** ——
`module.ts:279`：`const inst = this.di.resolve<object>(p.provide)`。

⇒ 用户侧写成：

```ts
// app.ts
export async function createApp({ workdir = DEFAULT_ROOT } = {}) {
  return agentia.createApp({
    discover: [...],                                    // 其余能力照旧自动发现
    providers: [
      { provide: 'WORKDIR', useValue: workdir },
      { provide: 'code-review', useClass: CodeReviewTools, deps: ['WORKDIR'] },
    ],
  });
}

// src/tools/code-review.ts
export class CodeReviewTools {
  constructor(private readonly root: string) {}          // ← 注入进来
  @Tool({ ... }) readFile(input: { rel: string }) {
    return safeResolve(this.root, input.rel);            // ← 守卫照旧，只是根变成运行期值
  }
}
```

**工具侧要写的东西和 C 一样多**（都是「读一个值」），但**框架一行不改**。

> 注意：`discover` 自动注册的 provider **没有 `deps`**（`discover.ts` 只给 `{ provide, useClass }`）。
> 所以要注入的能力得从 `discover` 挪到显式 `providers` —— 同一个 token 混用不会重复收集菜单
> （`module.ts:240` 的注释明确覆盖了这条）。

#### D 的两个真实代价（要写清）

1. **per-app，不是 per-run。** 它在 `createApp` 期定死。**在 D2 方向 I（重启式）下这没问题** ——
   每次 run 都重启子进程 ⇒ per-app 就是 per-run。但**方向 II（会话式、不重启）下不够用**，
   那时一个常驻进程要服务多个不同目录的 run。
2. **不进 `config.*` 快照** ⇒ trace 里没有这条。
   **但面板照样能显示** —— 因为 workdir 是**面板自己发出去的**，CLI 侧记一笔即可
   （「这条 run 是用 X 目录起的」）。丢的只是「生产环境的 run 也带这条」，
   而本方案要解决的本来就是**开发期**的可见性。

⇒ **结论：D 先行。** 它的代价恰好落在本方案的边界内（开发期 + 重启式），
而 C 的额外价值（per-run + 自动上 trace）要到 P3 才兑现。

#### C 的额外好处（**留给 P3**）：面板能免费显示「这次审的是哪个目录」

框架已有「生效配置快照」机制：`runConfigSnapshot`（`engine/run-config.ts:37`）把本 run 真正生效的
旋钮写成 run 根的 `config.*` attributes（`engine/loop.ts:242`）。`config.model` / `config.maxTokens`
就是这么来的。

⇒ `workdir` 作为 run 选项时，在快照里加一条 `config.workdir`，它就**自动落上 trace**，
面板的 `GET /api/runs` 直接读得到 —— **app 侧不用写任何代码**。

这同时满足了 D5 想要的「run 列表显示每个 run 审的是哪个目录」：50 条 run 扫一眼就知道各自动的哪棵树。
**B（env）方案做不到这一点**（env 不进快照），这是 C 相对 B 的第二个理由。

> 待定细节：`config.workdir` 记**绝对路径**还是 basename？trace 会流向 OTLP / Langfuse 等后端，
> 绝对路径会把本地目录结构带出去。见 §6。

**若真要动框架，C 是本仓正统形状**，理由能照抄现有字段：`AppOptions`（`module.ts:54`）已有
`toolTimeoutMs` / `maxEventChars` / `maxTotalTokens` / `maxCostUsd` 一族，每一个都落到
`ToolRunContext` 并要求**嵌套能力原样透传**（`@SubAgent` / `@Skill` 拉起自己的循环时）。
`workdir` 性质完全相同：**子 agent 里的工具必须看到与主循环相同的根**，
否则同一个 agent 在不同层级看到不同目录 —— 这与 `maxEventChars` 那条
「同一棵调用树上会出现两种截断口径」是**同一个形状**。

> 而 **D（DI）在这一点上其实是弱的**：DI 是 app 级单例，**子 agent 拿到的仍是同一个值** ——
> 所以「同一棵树同一个根」它天然满足；但**「主 agent 与子 agent 用不同根」它做不到**，
> 而这恰恰是 C 的透传语义能表达的。今天不需要，但值得记着这个差异。

形状（照现有惯例）：


### D6 · 对话历史从哪来（G4）

**需求**：输入框要带**历史对话记录** —— 面板上能看见整段对话，不只是当前这一句。
（如果还包含**输入回显**，即上箭头调出上一条 prompt，那是纯面板侧的小功能，可一并做。）

#### 先说一个已实证的坏消息

**trace 上既没有输入 prompt，也没有回复正文。**

| 想知道的东西 | 在 trace 上吗 | 证据 |
|---|---|---|
| 输入 prompt | ✗ | run 根 span 只有 `model` / `system.version` / `prompts.versions` / `session.id` / `stop_reason`（`engine/loop.ts:217-243,289`） |
| 回复正文 `finalText` | ✗ | 它只是 `runLoop` 的**返回值**（`engine/loop.ts:296`），且 `loop.ts` 里**没有任何** `recorder.event(rootId, …)` |

⇒ **面板不可能从 trace 拼出对话。** 历史必须来自一个**面板读得到**的地方。

#### 候选来源

| 来源 | prompt | 回复 | 评价 |
|---|---|---|---|
| **A. 文件后端 `SessionStore`** | ✓ | ✓ | **就是它**。框架已有概念（`runtime/session.ts:15`）；它是**真实对话**（模型下一轮真看到的那份）；跨重启存活 |
| B. inspector 自己的发送日志 | ✓（dev.ts 发的） | ✗ | 拼不齐 —— 回复不在任何面板可达的地方（子进程 stdout 走 `inherit`，进的是终端） |
| C. 把对话塞进 trace 的 `attributes` | ✓ | ✓ | **不要**。trace 是观测出口，会流向 OTLP / Langfuse 等后端 —— 把对话正文塞进根 attribute 等于**把用户对话发到观测平台** |

⇒ **结论：对话历史必须来自文件后端 `SessionStore`**（唯一能同时看到 prompt 与回复的来源）。

#### 但**先问一句：这个 agent 需要对话历史吗？**

按 §2.5 的两种形态，答案不同：

| 形态 | 需要对话历史吗 | 面板该显示什么 |
|---|---|---|
| **任务型**（code-review） | **不需要，而且是负担** —— 审完 A 仓库再选 B 仓库，把 A 的评审留在上下文里会串味 | **run 列表**（已有）+ prompt 回显 |
| **对话型**（助手 / 多轮） | 需要 | run 列表 **+** 对话流 |

⇒ **会话历史应当是「按需出现」**：app 用了 `session` 才显示对话视图，没用就不显示。
这样任务型 agent 得到干净的 run 列表，对话型 agent 两者都有。

⇒ **`FileSessionStore` 因此不是全局硬前置，而是「对话型 agent 的可选件」**。
它只在那类 agent 上才需要（放哪见 §6 待定 3）。

> 面板侧仍然**只读**会话文件、不写 —— 面板记的是「我发了什么」，模型看到的是「store 里有什么」，
> 两者一旦漂开（历史被裁剪、run 失败没回写、手动改了文件），面板就会显示一份**不存在的对话**。
> 这正是本仓一直在猎的那类静默不一致。

#### 约定形态（建议）

**固定相对路径** `.agentia/session.json`（相对项目根）：

- 子进程：`app.run([...], { session: { store: fileStore, id: 'dev' } })` —— 读它拼上下文，
  **成功**收尾时 append 回去（`runtime/run.ts:238` 只在成功轮次回写）。
- 面板：**只读**它来渲染对话。**不写** —— 写只发生在子进程，否则两侧都在 append，历史会乱。
- 该文件进 `.gitignore`（脚手架已生成的那个）。
- 面板侧的读接口：`GET /api/session`（与既有 `GET /api/runs` 同族，零依赖读文件）。

> 为什么不让面板直接记：面板记的是「我发了什么」，而模型看到的是「store 里有什么」。
> 两者一旦漂开（历史被裁剪、run 失败没回写、手动改了文件），面板就会显示一份**不存在的对话** ——
> 这正是本仓一直在猎的那类静默不一致。

> **评审补充（2026-09-22）· 失败 run 的显示语义**：`run.ts` 只在**成功**轮次回写 session
>（本节前文已引 `runtime/run.ts:238`）⇒ 失败的 run 不回写，面板若按「我发了什么」推，
> 对话就会静默缺一轮 —— 正是本节在猎的「显示一份不存在的对话」的同族。规则：
> 面板按 run 的实际终态显示（失败 ⇒ 该轮标失败标记），不假装那轮没发生、也不替 store 补写。

> **评审补充（2026-09-22 · 第二轮）· 「失败轮标失败标记」缺一个 join 键**
>
> 上一条规则说「面板按 run 的**实际终态**显示（失败 ⇒ 该轮标失败标记）」。但面板是从
> **会话文件**渲染对话的，而失败 run **不回写**会话（`runtime/run.ts:238` 只在**成功**轮次回写）
> ⇒ 那一轮在对话流里**根本不存在**，谈不上「标失败」。
>
> 要按这条规则显示，面板必须把 **run 列表**与**会话文件**对上 ——
> 键就在 **run 根 span 的 `session.id`**（正是本节开头那张表里列出的那个 attribute）。
> 落成具体形状：
>
> > 对话流的每一轮 = 「会话文件里的一条消息」**∪**「run 列表里 `session.id` 相同、
> > 但没有回写会话的（失败）run」
>
> 本文档没写这个 join，实现时八成会漏。漏了的症状正是本节在猎的那类静默不一致的**镜像版**：
> 显示了一份**少了**一轮的对话（而不是多了一轮）—— 同样是「一份不存在的对话」，
> 只是方向相反，而且更难发现（少的那个是失败那次，人天然会以为「它没跑」）。

### D7 · 面板布局（G4 落地形态）

今天是两栏：`grid-template-columns: 300px minmax(0, 1fr)`（`inspector-page.html:34`）——
左栏 run 列表、右栏调用树。

#### 结论：**run 列表留着**（此前建议「对话取代 run 列表」，按 §2.5 收回）

理由：对任务型 agent（code-review 就是），**run 列表就是主历史面** ——
它就是「历史」这个词在该形态下的正确含义。用对话流取代它，等于把用户要的东西换成不要的。

#### 布局改动：**run 列表 + 输入条，不新增第三栏**

```
┌──────────────┬──────────────────────────────────────┐
│ run 列表      │  调用树（trace-view 渲染）             │
│  （已有，保留）│                                      │
│  ▸ 12:03 ok  │   run / llm.turn / tool / …           │
│    ~/proj/a  │   能力 2/3                            │
│  ▸ 12:01 ok  │                                      │
│    ~/proj/b  │                                      │
├──────────────┴──────────────────────────────────────┤
│ [ 能力 2/3 ▾ ] [ 📁 ~/proj/c ] [ ☑ 多轮·trip-planner ]│   ← 第一行：这次 run 的配置
│ [ 帮我 review 一下代码                       ] [ ▶ ] │   ← 第二行：主操作

```

- **输入条固定在底部**，横跨两栏，**分两行**（四个控件挤一行会太窄）：
  - **第一行 = 配置**：**能力多选**（D8，显示「已选/总数」）+ **文件夹选择器** +
    **多轮开关**（初始值 = 所选能力声明的 OR，**开关上直接标出来源**，可覆盖）
  - **第二行 = 主操作**：**prompt 输入 + 运行**，占满宽度
- **`2/3` 这个计数不是装饰**：全选（`3/3`）时传 `undefined` 走全量路径，收窄时才传数组 ——
  一眼就能看出这次是「全量」还是「收窄」。
- **多轮开关带来源标注**（`多轮·trip-planner`）：混选时默认值是有歧义的，
  标注来源是为了**不让你面对一个「为什么这次带了上下文」的谜**（D8 ③）。

- **多轮开关决定「对话」视图出不出现**（§6 的 (甲)）：开 → 左栏多一个「对话」页签
  （默认仍是 run 列表）；关 → 不出现。**没配 session 也不出现** —— 不做空壳。
- run 列表每行**多显示目标目录与能力组合**（**都是 CLI 侧记账** —— 两个都是面板自己发出去的；
  见 D3-D 与 D8。P3 若改走 D3-C，目录那项会同时来自 `config.workdir`）。

`trace-view` 仍然只负责右栏那棵树，**`exports` 不变**（§2.2 的硬约束不受影响）。

### D8 · 调试的**单位**是「能力」，不是「app」（G5）

**背景**：一个 CLI 工程里可以有**多个** `@SubAgent` / `@Skill` / `@Prompt` / `@Tool`。
实际工程长这样：

```
src/subagents/trip-planner/     ← 行程规划（对话型）
src/subagents/code-review/      ← 代码评审（任务型）
src/subagents/weather/          ← 天气查询（一问一答）
src/skills/…  src/prompts/…  src/tools/…
```

⇒ 调试时你要的是**调试其中某一个**，或者**某几个的组合**，而不是每次都跑整包。
⇒ 面板需要一个**能力选择器**，三个档位：**单个 / 组合 / 全量**。

#### 机制已经存在（零框架改动）

`AppOptions.toolSources`（`module.ts:102`）是「只收集这些 token 的 provider 上的能力」白名单。
而 `discover` 给**每个能力文件夹一个 provider token**（`discover.ts:129`：
`{ provide: name, useClass: exported }`，`name` = 文件夹名）。

⇒ 一个选项覆盖三个档位：

| 档位 | 写法 |
|---|---|
| 单个 | `toolSources: ['trip-planner']` |
| 组合 | `toolSources: ['trip-planner', 'weather']` |
| 全量 | 不传（缺省扫全部） |

> **评审补充（2026-09-22 · 第二轮）· 收窄发生在**哪一层**：`createApp` 期还是 per-run**
> —— ✅ **已拍（2026-09-22）：走 A** —— 它决定 runner 的形状
>
> D8 选 `AppOptions.toolSources` 收窄，而 §D9 那张表（「四个控件谁来驱动」）把它标成
> 「谁能设 = **`createApp` 调用点**」。但 D2 的评审补充把方案推向**合并形态**
> （runner 常驻 + IPC 收 run 指令 + **只在代码变更时**重启），并明确要躲开
> 「每次 run 重新 `createApp` ⇒ 重付 discover + **MCP 握手**」这笔**装配税**。
> ⇒ 两条放一起就有张力：**换一次能力选择就要重付一次装配税**。
> （⚠️ 这条张力是本节初稿的立论。**同日实测后它基本消解**：所谓「装配税」是毫秒级，
> 见下面的探针表 —— 但换能力选择仍然要**重启进程**，理由换成了回收口。）
>
> **两条现成的路（都零框架改动）**
>
> - **A · `AppOptions.toolSources`（本文档现选）** —— token 级白名单，装配期只收集这些
>   provider 上的能力。一次收窄**顺带**把装配期静态校验（菜单查重、`tools` 引用存在性）
>   与 `prompts.versions` 那本账（`module.ts:217-221`）一起收窄。
> - **B · `RunAppOptions.tools`** —— per-run，语义是**覆盖整份工具菜单**
>   （`toolkit/module.ts:111`；engine 侧 `spec.ts:71` 的原话：「覆盖整份工具菜单
>   （裸工具同样过应用装配的中间件链 —— **不是旁路**）」）。凑子集的料也全是公开面：
>   `AgentApp.container` 公开 getter（`module.ts:438`）、`Container.registered(): Token[]` 公开
>   （`container.ts:135`，注释写着「调试辅助」）、`collectTools` / `collectSkills` + `skillToTool` /
>   `collectSubAgents` + `subagentToTool` / `collectPrompts` 全是公共导出（`src/index.ts:124-136`）。
>
> | | 好处 | 代价 |
> |---|---|---|
> | **A · `toolSources`** | 简单；语义正好就是「按 token 收窄」；连静态校验与 prompt 版本表一起收 | **换选择 = 重建 app**（实测 2.6 ms；真麻烦的不是时间，见下方的回收口） |
> | **B · `RunAppOptions.tools`** | 换选择**不用重启**，与合并形态天然契合 | **它不是 token 级** —— CLI 得自己把 token 翻译成菜单（见建议 1）；另需验与 A 路径等价 |
>
> ⚠️ **先把频率说准（修正本条的初稿）**：初稿写「调试时改得最勤的恰恰是『这次调哪个能力』」，
> **说重了**。对任务型能力（code-review / weather），「调哪个能力」是**会话级**动作 ——
> 选完之后就是反复换**文件夹与 prompt**（D7 的输入条正是这个形状）。
> ⇒ 张力是真的，但量级是「**一次会话几次**」，不是「每次 run」。下面的结论按修正后的频率给。
>
> **✅ 已拍（2026-09-22）：走 A，不走 B。**
>
> 1. **判据只有一条，而且本文档 D9 已经用过它：逻辑副本会漂移。**
>    那一条否掉了「把 dev harness 放用户工程」（每个工程一份副本，CLI 升级时它不会跟着变）。
>    套到 D8：`toolSources` 是 token 级（框架为这个诉求准备的缝），而 `tools` 是**整份菜单覆盖**
>    ⇒ 要让面板按 token 收窄，CLI 必须**把 `createApp` 的收集路径在 CLI 里复制一份**
>    （collect* + 容器解析 + 收集顺序 + 去重口径）。而本仓接受重复实现的方式是
>    **配一份逐字对拍守护**（先例：`packages/cli/src/diff.ts`、`harvest.ts`）
>    ⇒ 长期成本从「一次」变成「**每次改收集路径都要同步两边**」。
> 2. **B 会让「面板说的」与「装配做的」不一致**：静态校验与 `prompts.versions` 一律发生在
>    **全量**装配下 —— 面板显示「只调了一个」，装配其实做了全套。
> 3. **A 的代价有实测兜底**：进程内重建 app 是**毫秒级**（见下面的探针）——
>    比本节初稿假设低约两个数量级。⇒ 初稿那条「因为贵所以必须加配套」的理由**作废**；
>    配套**仍然要留**，但理由换成资源所有权（见下面的配套段与第三轮补充）。
>
> **配套形状（保留，但理由已换）**：四个控件按「要不要重建 app」分两类，面板**显式**区分 ——
> 能力选择（`toolSources`）**要**重建（会话级动作，重建一次）；文件夹 / prompt / 多轮开关
> **不要**（只起新 run）。⇒ **合并形态仍然成立**：只有你主动改能力选择时才付一次装配税。
> 重建 app 不丢会话历史（由 `SessionStore` 承担，正是 D6 的结论）。
> ⚠️ **理由换过一次，别再用旧的**：初稿的理由是「重建贵（每次几秒）」—— 实测 2.6 ms，
> 这条**不成立**。现在的理由是**资源所有权**：框架没有 `AgentApp.close()`，进程内重建会攒孤儿
> MCP 子进程 ⇒ 两类的实现是「**重启进程**」与「不重启」（见紧邻的第三轮补充）。
> 所以这条配套**不是为省时间**，别把它当性能优化拿掉。
>
> **什么时候该回头改走 B**：实测之后，「成本」这条理由基本没了（3 ms 级，就算变成每 run 一次
> 也不痛）。剩下的理由是**状态**：能力选择若真要按 run 变，而该工程的 provider **构造期就持有
> 非可重建资源**，那 A 的「重建 app」会连 provider 实例一起重建 —— 于是每 run 重付一次那笔资源。
> ⚠️ 这正是本探针暴露的一条硬约束：**MCP 连接器等「与 session 同寿」的资源，不能由 provider 的
> 构造函数创建**（那样它就跟 app 同寿了，每次重建都重 spawn，78 ms + 旧进程泄漏）。
> 正确形态是**从外面注入**（`providers: [{ provide: 'mcp-time', useValue: { client } }]`，
> runner 持有 client），这样重建 app 只重解析实例、不动连接。
> 若走到「按 run 变菜单」那一步，也不该让 CLI 复制一段收集路径 —— 应当**把 token→菜单的翻译
> 做进框架**（返回 `AgentTool[]` 的公共 API）。
>
> **动工前的探针（已跑 · 2026-09-22）** —— 初稿的假设被实测**否掉了**，见下。
>
> ① **走 A 时最该量的一件事** —— 一次「重建 app」的真实代价（含 MCP 握手）。
>
> 探针：`scripts/bench-app-assembly.ts`（本次在 `git worktree --detach` 的 HEAD 副本上跑，
> 零 token、零网络；MCP 侧是本地夹具 `scripts/mcp-fixture-server.py`）。
> 夹具照**真实工程**形态循环造四类能力（`@Tool` / `@Prompt`+真读 `.md` / `@Skill`+`tools` 引用 /
> `@SubAgent`+`asset(system)`+`tools` 引用），并挂 2 条直通中间件；
> 每次跑都打印自检行（providers 20 · 全量菜单 20 条 · 收窄后 1 条）**防真空变绿**。
> 环境：macOS / Node 26 / n=25（整进程档 n=5）：
>
> | 刻度 | 实测 |
> |---|---|
> | 进程内重建：纯装配（providers 已在手） | **0.4 ms** |
> | 进程内重建：发现 + 装配（import 缓存热）= **A 的每次重建** | **2.6 ms** |
> | 同口径收窄到 1 个能力（`toolSources: ['cap-000']`） | 2.7 ms |
> | 菜单规模敏感性：60 个能力 / 120 个能力 | 6.1 ms / 10.6 ms（≈0.08 ms/能力） |
> | MCP 冷（**新**连接器：spawn + initialize + tools/list） | 78 ms |
> | MCP 热（**复用**连接器：仅一次 tools/list 往返） | **0.3 ms** |
> | 整进程重启：仅 node+tsx 启动（零装配） | 494 ms |
> | 整进程重启：+ 发现 + 装配（框架走 **dist**，即发布形态） | **674 ms** |
>
> **三条结论，一条推翻了初稿**
>
> 1. **初稿「MCP 重的项目每次几秒」不成立 —— 高估约两个数量级。** 进程内重建 app 是
>    **毫秒级**（20 个能力 2.6 ms、120 个 10.6 ms，且真·四类能力混合形态与最轻形态差在噪声内）。
>    那笔「几秒」其实属于**整进程重启**（~0.67 s），而那正是合并形态要躲开、A 并不付的东西。
> 2. **MCP 那笔税取决于「连接器跟谁同寿」，不是「重建 app」本身。** 握手在
>    `mcp-stdio.ts:216` 的 `ensureReady()` 里**记忆化**（spawn 也是惰性的）：只要面板让连接器
>    活过重建，一次重建只多付**一个 `tools/list` 往返 = 0.3 ms**；只有把连接器也重建了才付 78 ms。
>    ⇒ 面板/reunner 的持有关系里，**连接器应当与 session 同寿，而不是与 app 同寿**。
> 3. **「换能力选择要不要重建 app」这个区分仍然要做 —— 但理由不是成本，是资源所有权。**
>    实测确实把「重建很贵」这条理由拿掉了（2.6 ms），可它立刻被一条更硬的理由替上：
>    框架**没有** `AgentApp.close()` / `dispose()`（`module.ts` 全文无此方法），而 MCP 连接器
>    是**用户代码**创建并持有的（`mcp.ts:21` 的用法）⇒ 进程内反复重建会攒下孤儿 MCP 子进程。
>    见紧邻的第三轮补充：「能力选择变化 = **重启进程**」。
>    两条合起来才是完整结论：**成本上进程内重建几乎免费，但今天没有回收口，所以仍走重启**；
>    等框架真长出 `app.close()`（或 runner 自己持有连接器）再谈进程内重建 —— 那时它是个
>    **2.6 ms 级**的动作，不再是「几秒」。
>
> **边界（这些数字不覆盖的，别拿它当结论）**
>
> - 只量了**「换能力选择」**。**改能力代码**不在内：Node 的 import 按 URL 缓存，常驻 runner
>   收不到源码改动（这正是 D2「只在代码变更时重启」的由来），而那一次重启要 ~0.67 s。
>   ⇒ A 不把这条变坏，也不解决它。
> - **反复重建的资源回收没有裁判**：每次 `createApp` 都新建一个 `Container` 并重新 resolve
>   provider 实例。重建 N 次就产生 N 份实例；旧 app 持有的 MCP 连接器 / 定时器 / 自定义资源
>   需要一个明确的回收责任方，否则是慢泄漏。
>   ✅ **已定（2026-09-22）**：不靠「谁来 close」，靠**所有权约定 + 进程级生命周期** ——
>   见 D9「(d) 附一条硬约定」（连接器在模块作用域创建并注入；今天仍以「重启进程」收编子进程）。
>   本探针只证明**成本**不是障碍；回收口这一条由 D9 的约定接管。
>
> ② 若最终改走 B，则要验：收窄后的菜单与 `toolSources` 路径**逐项一致**（能力名集合、顺序）·
> 中间件链照样过（`spec.ts:71` 承诺了，但要实测）· `prompts.versions`（`module.ts:217-221`）
> 在两条路径下取值相同 · 孤儿能力告警（`module.ts:410-429`）的行为差异。
>
> **它为什么必须在 P1a 之前定**（✅ 已定，见上）：它决定 runner 的接口形状 ——
> 「每 run 建一次 app」与「建一次 app、每 run 传菜单」是两种不兼容的形状，
> 拖到 P1c 再改等于把 P1a 重做一遍。

> **评审补充（2026-09-22 · 第三轮）· 「重建 app」必须写明是**重启进程**，不是进程内重建**
>
> 上面「走 A + 能力选择变化才重建 app」与 D2 的合并形态（runner 常驻）放一起有一个资源坑：
> **进程内重建 app 会泄漏旧 app 的 MCP 子进程**。`AgentApp` **没有** `close()`/`dispose()`
> （`module.ts` 全文无此方法），而 MCP 连接器是**用户代码**在 `app.ts` 里 `mcpTools(mcp, …)`
> 时创建并持有的（`mcp.ts:21` 的用法示例），框架从不拥有它 —— runner 拿不到、也关不掉。
> 常驻进程里每换一次能力选择就多一批孤儿 MCP server。
>
> ⇒ 落成具体形状：**能力选择变化 = 重启 runner 进程**（会话级动作、频率低，重启可接受，
> 且进程死亡连带收编子进程 —— 这正是 D2 风险行「kill 要连整棵树」的纪律覆盖的地方）；
> 文件夹 / prompt / 多轮开关 = 常驻进程内新 run。这样「控件分两类」的结论不变，
> 但两类的实现分别是**重启**与**不重启**，零框架改动保住。
> （若哪天框架长出 `app.close()`，进程内重建才成为可选项 —— 那是 P3 材料，现在不为它动公共面。）
>
> **同日的探针给这条补充了两个数字**（见上方 D8 探针表）：
> ① 「重启进程」这一档实测 **674 ms**（框架走 dist、20 个能力），与 D2 方向 I 里那句
>    「重启开销 → ~0.7s，可接受」**独立吻合** —— 且其中 ~494 ms 是 node+tsx 启动本身，
>    装配只占 ~180 ms。⇒ 要再快就该啃**启动**，不是啃装配。
> ② 反过来说：**进程内重建的成本已被证明不成问题**（2.6 ms）。
>    ⇒ 卡住「进程内重建」的**只有回收口这一条**，不是性能 —— 所以这里的结论要读成
>    「**今天**必须重启」，而不是「重启是更优的性能选择」。哪天有了 `app.close()`，
>    这条决策的成本侧已经完全不是障碍了。

#### ✅ 「单个」≠「绕开主 agent」—— 这是**设计**，不是妥协（2026-09-22 用户确认）

技术上确实绕不开：`subagentToTool` 的 `run` 在拿不到 engine 注入的 `ToolRunContext` 时
**直接抛错**（`subagent.ts:114-118`：「subagent "x" 只能在主 agent 运行中被调用」）；
`skillToTool` 同样（`skill.ts:123-127`）。

**但用户已明确：不应该绕。** 所以这条不再是「待权衡的限制」，而是**方案的前提**。

⇒ **框架不需要新增任何 API。** 「纯隔离」（不经过主 agent、省掉那次 turn）**已否决**，
不做 capability runner（§7）。

##### 这个决定带来一个必须写清的含义

既然主 agent 永远在环里，**你调试的其实一直是两样东西**：

1. **主 agent 的分发决策** —— 它有没有挑中你要调的那个能力？
2. **被选中的那个能力** —— 挑中之后它做得对不对？

这**恰恰是真实路径**，也恰恰是 trace-view 的用武之地：你能在调用树里看到
「主 agent 想调谁 → 传了什么参数 → 子 run 里发生了什么」。

**但它也意味着一个失败模式必须被看见**：如果主 agent 的 `description` 写得不好，
它**根本不会调**你选的那个能力 —— 你会看到一次「主 agent 自己答完了」的 run，
而没有任何报错。**这不是 bug，是你要调的东西。** ⇒ 面板的「能力选择器」在调试时的作用
**不是「隔离」，而是「减少干扰」**：菜单收窄后主 agent 更容易挑中你要调的那个，trace 也更短更易读。

> 顺带一个边界：被 `toolSources` 排除的能力**不是绝对不可达** ——
> 其他能力的 `tools` 显式引用仍能调它（`module.ts:410-429` 的「孤儿能力告警」讲清了这条边界）。
> ⇒ 「我明明没选它，它怎么被调了」的答案通常在这里。

#### 多轮：**按能力变，不是按工程变**（修正 §2.5）

上一版把「任务型 / 对话型」当成**工程级**属性，这是错的 —— 同一个工程里三种都要：

| 能力 | 多轮？ | 为什么 |
|---|---|---|
| 行程规划 | **要** | 「改成 3 天」「住宿换民宿」——追问是常态 |
| 天气查询 | 基本不要 | 一问一答 |
| code-review | 不要 | 每次独立，跨仓库会串味 |

⇒ **「要不要多轮」是每个能力各自的属性**，但它**落到运行时仍是 per-run 的开关** ——
框架侧天然支持：就是 `app.run(msgs, { session })` 的**有无**（`module.ts:158`），本来就是 per-run 的。

⇒ 所以正确形状是**两层**：
1. **能力声明默认值**（`trip-planner` 声明「我多轮」）—— 这是它的属性，不该每次重定；
2. **面板允许为这次调试覆盖**（调试嘛，就是想试试开/关的区别）。

只做 1 会太死，只做 2 会让你每次手动勾（且容易忘，跑出一个「串味」的假象）。

#### 形态已定（2026-09-22 用户确认）：**多选** + **显式声明**

##### ① 多选 —— 面板对能力 token 做多选

| 细节 | 决定 | 为什么 |
|---|---|---|
| 默认状态 | **默认全选**（= 全量） | 菜单先完整、再收窄；比「空选 = 全量」少一次困惑 |
| 全选时传什么 | 传 `undefined`（走缺省全量路径） | 与「不传即全量」同义，且省掉一次白跑的孤儿检查（`module.ts:413`） |
| 发送顺序 | **按固定顺序**（目录序 / 字典序），**不用点击顺序** | 调试要可复现 —— 否则同一组能力两次跑出不同菜单序 |

**可复现性怎么保证**：`toolSources` 是**数组**，不是 `config.*` 的标量 ⇒ 上不了
`runConfigSnapshot` ⇒ 走 **CLI 侧记账**（与 workdir 同一条路），run 列表显示「这次开了哪几个能力」。

> 多选放大了 D8 开头那条边界：选了 A，A 的 `tools` 若引用了 B，**B 仍可被调用**
> （`module.ts:410-429`）。选得越窄，越容易撞上「我没选它它怎么被调了」——
> 答案通常在这里，而不是在 `toolSources` 的实现里。

##### ② 显式声明 —— 先说清它**本来就是 dev-only 的知识**

生产里**没有能力选择器**：一次对话就是一个 session，模型在对话内自己路由。
⇒ 「每个能力各自多轮」只在**调试时**才成立 ⇒ 它属于 **dev 配置**，不属于能力定义。

所以声明落在 **`src/dev.config.ts`**（模板生成，**只有数据，没有逻辑**）：

```ts
// src/dev.config.ts
export default {
  /** 这些能力按多轮调试（累积 session）；未列出的按单轮。 */
  multiTurn: ['trip-planner'],
};
```

**为什么是「数据文件」而不是「逻辑文件」** —— 这正是 D9 里 `dev.ts` 被否掉的同一个判据：
**逻辑副本会漂移**（CLI 修了 bug，工程里那份不知道），**数据声明不会**。
⇒ 规则：**`dev.ts`（逻辑）不要；`dev.config.ts`（数据）可以。**

**为什么集中一张表而不是每个能力一个文件**：显式性的要点是「**一眼看全策略**」。
「忘了声明」的坑由 D8 的两层结构堵住 —— 忘了就是单轮（安全默认），而面板上那个开关就在手边。

**默认值**：文件缺失 ⇒ **全部单轮**。任务型是安全默认（不会串味）；
「默认全选」说的是菜单完整，两者不冲突：**菜单给全，但每个能力默认单轮**。

##### ③ 混选怎么办（**多选带出来的新边界**）

多选之后必然出现「`trip-planner`（多轮）+ `code-review`（单轮）同选」。
此时**默认值是有歧义的** —— 不能让面板静默猜一个。

⇒ 规则：**多轮开关的初始值 = OR（所选能力里只要有一个声明多轮，就默认多轮），
且面板必须把来源标出来**（例如「多轮 · 因为 trip-planner」）。

这与本仓一贯的偏好一致：**不要静默行为**。宁可多显示一句来源，
也不要让用户面对一个「为什么这次带了上下文」的谜。

### D9 · 这四个控件**谁来驱动**（本方案真正的设计题）

把 D2 / D3 / D6 / D8 的四个控件摊开看，会发现同一个形状：

| 控件 | 落到哪 | 谁能设 |
|---|---|---|
| 能力选择 | `AppOptions.toolSources` | **`createApp` 调用点** |
| 多轮开关 | `app.run` 的 `session` | **`app.run` 调用点** |
| 目标文件夹 | `workdir`（D3） | **`createApp` / run 调用点** |
| prompt | `messages` | **`app.run` 调用点** |

⇒ 四个全是 `createApp` / `app.run` 的选项。框架**不能**替它读 env —— 那是 spec §9.3（`spec.md:177`）
与 §10 已锁的决策（「框架不读 env、不含 dev 逻辑」），也是 `env.ts:17-22` 讲清的道理。

#### 关键转折：**「用户代码」和「调用者」不是一回事**

上面那张表我一开始读成了「只有用户代码能设 ⇒ 模板里必须长出 dev 逻辑」。
**这是错的。** 真正的约束是「**调用者**能设」。

⇒ 如果 `agentia dev` **自己 import 用户的 `src/app.ts` 并调用它**，那么
**CLI 就是调用者** —— 四个控件它全都能设。**用户工程里一个 dev 文件都不需要。**

唯一的要求是：`app.ts` 导出**一个接受选项的工厂**。

#### 四个方案

| 方案 | 形态 | 评价 |
|---|---|---|
| **(a) 模板长出 dev harness** | `main.ts` 里读一份 dev 配置，应用到那四项 | 可行，但 `main.ts` 从 38 行涨成 ~70 行，且 dev 与生产逻辑混在一起 |
| **(b) 拆三个文件** | `app.ts` / `main.ts` / `dev.ts`（dev harness 在**用户工程**里） | harness 可整份删掉，但它是**用户工程里的一份 dev 副本**：会被提交、会漂移、CLI 升级时它不会跟着变 |
| **(c) preload 猴补** | 在 preload 里改 `createApp` 的入参 | **否**。脆弱（依赖内部形状）、且把 dev 感知往框架推 |
| **(d) 只拆 `app.ts`，harness 留在 CLI** ← **已定** | `app.ts`（导出工厂，接受四个选项）+ `main.ts`（薄入口）；**没有 `dev.ts`** | dev 逻辑留在**它该在的地方**；模板变更最小；CLI 升级时 harness 自动跟上 |

**(d) 怎么跑**：`agentia dev` 用用户的 `tsx` 起一个 **CLI 自带的 runner**（不是用户工程里的文件），
runner `import` 用户的 `src/app.ts`，从 IPC 收面板指令 → 调 `createApp({ toolSources, workdir })`
→ `app.run(messages, { session })` → trace 走 `POST /ingest`。`main.ts` 完全不知道 dev 的存在。
多轮的**默认值**从 `src/dev.config.ts` 读（D8 的「显式声明」），**存在才读、缺省全单轮**。

> **评审补充（2026-09-22）· dev 环的预算护栏缺省**：runner 驱动 `app.run` 时应带一个**保守的
> 缺省预算**（`maxCostUsd` / `maxTotalTokens`，如 $1 / 次 run），面板输入条上可见、可改。
> `POST /run` 让「点一下就跑一次真 agent」成立，而真 agent 真花钱 —— 一个跑偏的循环就是
> 一张账单。这与框架既有的预算策略同一条路（`runConfigSnapshot` 会把生效预算写进 trace，
> 面板读得到），不是新机制 —— 只是 runner 替「还没想到要配」的开发者先把护栏立上。

**(d) 顺带解决了 D8 的「菜单从哪来」**（原 §6 第 6 问）：
- `AgentApp.container` 是**公开 getter**（`module.ts:438`），`Container.registered(): Token[]`
  也是公开的（`container.ts:135`，注释「调试辅助」）⇒ **CLI 自己就能列出 token**。
- 而 token 就是**能力文件夹名**（`discover.ts:129`）。⇒ 让 `app.ts` 顺便 `export const CAPABILITY_DIRS`
  （它本来就算了这个数组），CLI `readdir` 这些目录即得菜单 —— **两侧同一个常量，不会漂移**。

**(d) 的代价**：

1. **用户不能自定义 dev 行为**（注入假 client、预置 fixture 之类）。
   ⇒ 留一个**数据逃生口**：`src/dev.config.ts`，**存在才读**（形状见 D8 的「显式声明」）。
   默认零样板，需要时才写。**它是数据不是逻辑** —— 逻辑副本会漂移，数据不会（D8 有这条判据）。
2. ⚠️ **子进程的 cwd 必须仍是项目根**（**最容易踩的一条**）：
   `loadEnvFile()` 按 cwd 找 `.env`（`env.ts:126`），`discover` 的相对路径也按 cwd（`discover.ts:52`）。
   CLI 自己 import 用户 app 时，**不能**把子进程 cwd 设成「agent 工作目录」——
   否则 `.env` 会静默读错。这正是 §2.3 那个坑的又一次现身，也正是 A（chdir）方案被排除的同一个原因。
3. **模板破坏性变更**（与 (b) 相同）：老工程要拆出 `app.ts`。

**（d）附一条硬约定 · 连接器/外部资源在模块作用域创建并注入**（2026-09-22 定）

`app.ts` 里凡属**进程外资源**的（MCP 连接器最典型；sqlite 句柄、定时器同理），必须在
**模块作用域**创建、以 `useValue` 注入给能力；**不许在 provider 的构造函数里创建**。

- **为什么**：dev runner 换能力选择时会**重建 app**（D8 已定 A）。构造函数里建 ⇒ 资源跟 **app**
  同寿 ⇒ 每次重建重 spawn（实测 MCP 冷握手 **78 ms**）+ 旧子进程变孤儿（框架没有
  `AgentApp.close()`，见 D8 的第三轮补充）。模块作用域建 ⇒ 资源跟**进程**同寿，
  重建只是重解析 provider 实例、不动连接。
- **正确形态**（也就是模板该生成的形状）：

```ts
const mcp = createStdioMcpConnector([...]);   // 模块作用域：全进程只建一次

export const createAgentApp = (opts: AppOptions-ish) =>
  createApp({
    providers: [{ provide: 'mcp-time', useValue: { client: mcp } }],  // 注入，不是自建
    // …
  });
```

- **收益不只是避坑**：这条约定一成立，「重建 app」就退化成纯 CPU 动作（实测 **2.6 ms**，
  复用连接器再加 **0.3 ms**）。今天仍走「重启进程」**只是**因为没有 `app.close()` ——
  这条约定是把 A 从「必须重启」解锁成「重启可选」的**前提**。
- **两种接线形态都要守这一条**（都得写成模块作用域，别只守一种）：
  1. **裸工具**（**文档里现在写的用法**，`mcp.ts:21`）：`tools: await mcpTools(mcp, { server: 'time' })`
     —— `mcp` 建在模块作用域时，重建只是**再取一次 `tools/list`（0.3 ms）**，不 spawn。
  2. **provider 注入**：`providers: [{ provide: 'mcp-time', useValue: { client: mcp } }]`，
     或 `useClass` + `deps`（仓里已有先例形状：`scripts/e2e-mcp.ts:107` 的 `constructor(client)`）。
  ⇒ **要拦的反例**：`new XxxConnector()` / `await mcpTools(newConnector)` 写在某个 provider 的
  `constructor` 里或写在每次重建都会重跑的那层 —— 那才是「跟 app 同寿」。
- **不是新机制**：`deps` + `useValue` 都是现成 DI（`container.ts:16-21`），与 D3-**D** 走的是同一条路。
- **对老工程的检查点**（可选，先不承诺）：`agentia doctor` 可以静态体检「有 MCP 能力但连接器
  建在构造函数里」这种形状并提示。新工程由模板直接生成正确形状，所以这是**迁移期**才需要的东西。

**为什么 (d) 比 (b) 好**：harness 放用户工程里，等于**每个工程一份 dev 逻辑的副本** ——
CLI 修了 bug、加了能力，那些副本一个都不会变，而它们又不会被任何人主动维护。
放在 CLI 里，升级 CLI 就等于升级 harness。

**迁移代价要说清**：模板结构变更 ⇒ **已生成的工程需要按新模板改**（与 v0.8.0 那次
「脚手架 discover 生产路径修复」同类，`spec.md:2630`）。这是一次**破坏性变更**，
要写进 CHANGELOG 的迁移小节。好在拆分是**机械的**：把 `createApp` 那段搬进 `app.ts`、
包成接受选项的工厂，`main.ts` 只留「调它 + 处理 result」。

> **评审补充（2026-09-22 · 第二轮）· 破坏性模板变更的**版本口径**与**发布面**（原 §D9 只提到 CHANGELOG）**
>
> 1. **版本落 minor，不是补丁位。** §D9 说「要写进 CHANGELOG 的迁移小节」，但没说版本口径。
>    按本仓**已定口径**（补丁位只用于 additive、**破坏性变更才进 minor**）：
>    「老工程要拆 `app.ts` + `main.ts` 变薄」是**破坏性**的 ⇒ 这次落 **minor**（按当时的线即 `0.9.0`），
>    并在 CHANGELOG 有迁移小节。写成「0.8.x 补丁」会让老工程在 `npm update` 时**静默**换到新结构。
> 2. **模板文件在发布面里，别漏。** `scripts/release-surface.mjs` 已含
>    `packages/cli/templates/package.json` 的**两条替换面**（`:65` / `:71`），另有 `STRUCTURAL` 结构面清单
>    （`:297` 打印「N 项替换面 + M 项结构面」）。本方案会新增 `templates/src/app.ts`、
>    `templates/src/dev.config.ts`、改动 `templates/src/main.ts` ⇒ **要核这两份清单**：
>    漏了不会响亮失败（闸门只校验清单**里**那些项的计数），只会**静默**留下一个没被守住的发布面
>    —— 这正是本仓一直在猎的那类失效。
> 3. **迁移说明要给出可比对的判据**，不能只说「按新模板改」：老工程的 `main.ts` 与
>    新模板的 `app.ts` 之间的映射是**一段代码搬家**，所以迁移指引应当写成
>    「把 `main.ts` 里 `createApp(...)` 那一段整体移入 `app.ts` 并包成接受选项的工厂；
>    `main.ts` 保留 ① 读 `.env` ② 调工厂 ③ 处理 `result.error`（含退出码）」——
>    ①③ 的顺序与语义都不能变，否则会把 `templates/src/main.ts:29-36` 那条
>    「run 失败不抛 ⇒ 不检查就是打印空白 + 退出 0」的坑原样带进新结构。

**已定 · 「历史」的读法：两层都要**（2026-09-22）

**(1) 「历史」的读法** —— 用户说「输入框要有历史的**对话**记录」，但 code-review（任务型）
说明**会话历史对它是负担**（跨仓库串味）。而新例子里的**行程规划**又确实需要多轮。

**问题的根源是：这两件事都叫「历史」，但它们根本不在一个层面上。**
一句话区分 —— **(乙) 解决「手」的问题，(甲) 解决「脑」的问题**：

| 读法 | 是什么 | **模型看得见吗** | 谁需要 |
|---|---|---|---|
| **(乙) prompt 回显** | 输入框记住打过的 prompt，上/下箭头或下拉调回（像 shell 历史） | **看不见** —— 只是把文字填回输入框，你还能改；模型收到的仍是你最终回车的那句 | **全部**（尤其任务型：`↑` 调回固定命令 → 回车） |
| **(甲) 对话历史** | 面板显示整段多轮对话（session 累积） | **看得见** —— 前面说过的话进模型上下文（有代价：更长、更贵、可能被裁剪） | 对话型能力（行程规划）—— **多轮开关打开时** |

**为什么必须分开（两个方向都错）**：

- **只有 (甲)**：任务型 agent 会显示一个「对话」面板 ⇒ **误导**你，让你以为上个仓库的评审
  被带进这次了。它没有，而且不该有（D6 的「显示一份不存在的对话」）。
- **只有 (乙)**：对话型能力真的没法追问。
- **没开多轮时不该有 (甲)**：一次 run = 一句输入 + 一段输出，**没有「历史」这回事** ——
  而那个东西 run 列表已经在显示了。凭空多一个对话视图就是上面那种误导。

**建议**：(乙) 永远有；(甲) 跟「多轮开关」走（开了才出现对话视图，没开就只有 run 列表）。
落到界面（D7 的输入条）：`[ 能力 2/3 ▾ ] [ 文件夹 ] [ 多轮·来源 ] [ 输入框 ↑/↓ ]`
—— 输入框负责 (乙)，多轮开关决定 (甲) 出不出现。

## 7. 明确不做

- **多项目 studio / 面板里选项目**：那需要一个常驻服务 + 项目切换器，
  且要完整背上 D0 的全部安全负担。独立立项，不在本方案内。

  只帮得到 cwd 相对的工具，还会连 `.env` 一起搬。**本方案走 D3-D（面板里选）则它不是必需品**。
  它若要做，只应定位成「免 `cd` 的便捷入口」。
- **能力直调（capability runner，绕过主 agent）**：**用户已明确否决**（2026-09-22：
  「肯定不能跳过主 agent 直接调用子 agent」）。这不是「暂时不做」，是**设计前提** ——
  「单个」的含义是**菜单收窄**，主 agent 永远在环里（D8）。
  ⇒ 本方案**不含任何框架 API 新增**。
- 面板里改代码 / 当编辑器。
