# demo 只要 5 分钟，敢不敢上线要看 trace —— 我为什么写了一个「把 agent 做成服务」的框架

> 大多数框架回答「它能做什么」。我想写一个回答「**你敢不敢放它跑**」的。
> 差别不在编排，在**可观测是不是一等公民**——我的答案是：四类能力决定它能做什么，**trace 决定你敢不敢上线**。

## 一、那条每个人都走过的曲线

做过 agent 项目的人都见过它：

- **第 1 天**：`while` 循环 + tool calling，五十行，demo 惊艳。
- **第 1 周**：接上真实业务，开始玄学——「昨天还好好的」「这个 case 它为什么突然不调工具了」。
- **第 1 个月**：你发现自己八成的时间不在写功能，而在反复回答三个问题：

1. 这次 run **到底发生了什么**？（几轮模型、每个工具入参出参、卡在哪一步）
2. 这次 run **花了多少钱**？（token 细分到每轮、缓存命中多少、哪个子 agent 在烧）
3. 这次改版**是变好还是变坏**？（换 prompt、换模型之后，回归怎么验）

这三个问题**全是观测问题，不是编排问题**。而它们的答案，在你选框架的那天就基本定下来了。

## 二、两条主流路线，都把观测放在外面

**编排派（LangGraph 为代表）**：核心是显式状态图——节点、边、checkpointer，编排能力目前同类最强。
但调用树不在框架里：要看 trace 接 LangSmith。于是「框架产出什么数据、数据长什么样」是为配合平台
而设计的——你买的其实是「框架 + 平台」的组合，观测那一半是平台功能。

**平台派（Langfuse 为代表）**：开源、可自托管、看板/数据集/评分都很成熟，观测侧做得最好之一。
但它是**平台**：数据质量取决于你的埋点。框架不管你的 run 结构——span 怎么切、成本怎么算、
`tool_use` 与 `tool_result` 怎么配对，全靠集成层和你自己。埋点埋歪了，看板再漂亮也是错的。

两条路线共享一个隐含假设：**可观测是外挂**。框架负责跑，观测是另一个系统的事，中间靠集成粘。
粘得好不好，上线那天才知道。

我想验证相反的假设：**trace 应该和能力声明同级**——它是每次 run 的必然产出，不依赖任何外部平台成立。

## 三、于是「trace 是一等公民」被我写成了四条硬承诺

**① 每次 run 必然产出一棵结构化调用树，零后端。**

```ts
const app = await createApp({ name: 'reviewer', discover: CAPABILITY_DIRS, system });
const { result, trace } = await app.run([{ role: 'user', content: '评审这个仓库' }]);
// trace：run 根 → llm.turn × N → capability（tool / skill / subagent）
// 每个 span 带 token 细分（input / output / cacheRead / cacheCreation）与成本估算
```

不写一行观测代码，`trace` 就在那里。落盘是一行 JSONL，CLI 直接消费：
`agentia report trace.jsonl`（哪个能力慢/贵/爱失败）、`agentia diff a.jsonl b.jsonl`（两次 run 的
调用树 A/B，有差异退出码 1）、`agentia dev`（本地面板：输 prompt、选能力、看实时调用树）。

**② 记账口径由框架统一守，埋点埋不歪。** 成本、token、错误分类（api / server / timeout /
aborted / unknown，决定可不可重试）、挂起与恢复，全走同一条引擎内记账路径。使用者的辅助操作
（记忆回写、会话追加、sink 投递）**永远击穿不了主路径**——这是写进架构守卫的原则，不是口号。

**③ 出口是一条缝，不是一套平台。** 框架只保证 `TraceSink { export(trace) }`：落库、脱敏、采样、
日志关联、送 Langfuse / OTLP——四条配方加一个示例就是全部（`docs/observability.md`）。
**我不建看板**：看板是各家的强项，我不想再造一个。

**④ 最关键的一条：trace 必须能参与「判」。** 前面三条给了「看」，而「敢不敢上线」要的是「判」。
所以除了 report / diff / harvest（把线上事故的 trace 回流成回归用例），
还需要一件东西：**把评测收成一个判据**——把这次的用例结论对上一版的基线比，回答「这一版能不能发」。
这件事我落地成了一份可拷走的实现（`docs/eval-gate.md` + `examples/eval-gate/`）：

- **回归**（基线通过、这次失败）⇒ 不通过；
- **删用例**（基线里有、这次没跑）⇒ 不通过——否则「删掉那条总失败的用例」就成了过闸门最省事的办法；
- **基线里本来就失败** ⇒ 放行（已知债不拦发布——闸门拦的是**新的**坏消息，不是替你把历史账一次清完）；
- 退出码三档：`0` 通过 / `1` 有回归或删用例 / `2` 基线坏了——**「基线文件坏了」不该被读成「我的 agent 退化了」**。

## 四、为什么这些能成立（工程上的三条纪律）

- **零运行时依赖**：框架、CLI、渲染器三个包的 `dependencies` 全空，只有 `node:` 内建。
  代价是能力要自己写；好处是你不用替我的依赖做安全审计，也不会有传递依赖和框架版本打架。
  这条有可执行守卫：往 `src` 里加一行 `import { z } from 'zod'`，`npm test` 当场红。
- **公共 API 只有一个出口**：`src/index.ts`。新增导出必须登记，官网 API 页有**双向**守卫
  （页面上写的必须真存在；代码里有的必须在页面上出现）。
- **「声称的守护」要能被证明**：仓库里的守卫逐条做过**反向验证**——把实现改回坏版本，确认
  那条用例真的变红，再还原。这条纪律救过我：`tests/engine/tracer.test.ts` 里那句
  「两条路同口径」的断言曾经是**自我比较**（永远绿），是逐行审计时才发现的。

## 五、我刻意没做的（以及为什么）

- **不做对话 UI**：定位是「交付可上线的服务，不是对话助手」。浏览器里那个是**调试面板**，
  不是产品界面。
- **不做进程级决策**：不读 `SIGTERM`、不自己加载 `.env`、不做配额与限流——那些是宿主的启动决策
  （示例里都接了，但框架不替你决定）。
- **不建看板/CMS/数据集管理**：出口给你，平台你选。
- **不假装能保证「更便宜」**：框架能保证的是**不浪费、不失控**（预算硬闸、上下文裁剪、
  背压收口、失败不重试去烧 token），单位价格是模型厂商的事。

## 六、现在到哪一步了（如实说，截至 2026-09-26）

- 版本 `0.9.4`，npm 上是 `@migor/agentia` 与 `@migor/cli`；三个测试套件 **1429 例全绿**
  （框架 1214 + CLI 188 + 视窗 27），
  本地与 CI 跑**同一条 8 步验证链**（类型检查 + lint + 构建 + 三套测试 + 五个 e2e + 官网产物校验）。
- 示例是**真跑**的，不是文档里的代码块：`examples/complete`（四类能力 + 三种触发 + 全观测栈）、
  `examples/deploy`（多阶段镜像 + 优雅停机 + 崩溃续跑）、`examples/code-review`（离线确定性 demo）、
  `examples/eval-gate`（上面那条发布判据）——它们都在 e2e 里被真启动、真断言。
- **基本没有人在用**（仓库 3 个 star、1 个 fork）。所以我只能把「值得」这件事挂在证据上：
  每条承诺都配了一条会红的用例，而不是配一段形容词。
- 还有明确的欠账：deploy 示例的**镜像**直到最近才有一条 CI 构建（此前 `docker` 在 CI 配置里
  出现 0 次），真实模型的花钱验证（`e2e:live`）**不进 CI**、要你自己带 key 跑。

## 七、如果你也做过那个「昨天还好好的」的排查

试试这个（Node ≥ 18）：

```bash
npx @migor/cli create my-app     # 生成工程（含 .env 与使用者向 AGENTS.md）
cd my-app && npm install
$EDITOR .env                     # 填 key
npm run dev                      # 本地面板：输 prompt / 选能力 / 看实时调用树与成本
```

跑一次，然后打开那棵调用树看一眼：**每个工具花了多少 token、在哪一轮、为什么失败**。
如果那一刻你想起的是「我上个项目要是早点有这棵树就好了」——那这个框架就是为你写的。
